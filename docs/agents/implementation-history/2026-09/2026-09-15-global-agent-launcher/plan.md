## Prior Project Context

`ledger_get_repository_context` surfaced the workspace's declared short-term strategic goal: make setup and daily usage as frictionless as possible for developers. This plan is a direct instance of that goal — it removes the recurring manual step of looking up an agent's frontmatter `name:` slug and typing `claude --agent <slug>` by hand. `ledger_search_insights` returned no prior insights on CLI launcher UX, frontmatter parsing, or agent-picker design, so there is no existing guidance to reconcile against and no history of related pitfalls to avoid.

## Summary

Add a new `agent` subcommand to the existing global `ai-insights` CLI (`ai-insights agent`, already deployable to any terminal via the documented `npm link` flow) that scans the user's `~/.claude/agents/` directory, presents every deployed persona in a type-to-filter interactive picker, and launches `claude --agent <slug>` with the selection. Display labels prefer each agent's pretty `role:` frontmatter field (present on the 9 ledger-suite personas) and fall back to the filename without its extension for the 34 standalone/ledger-support personas that have no such field — exactly the two-tier rule requested. The picker degrades to a numbered non-interactive prompt when stdin isn't a TTY (CI, piped input), matching the conventions already established by `@mistralys/cli-menu` (the zero-dependency library this workspace already uses for all its other interactive TUI elements).

## Architectural Context

The workspace exposes exactly one global CLI binary today: `ai-insights`, wired via the root `package.json`'s `bin` field to `scripts/cli.js`. Once a developer runs `npm link` from the repo root (documented in `docs/references/development.md`), `ai-insights <command>` works from any directory on any of the three supported OSes — npm generates the Windows `.cmd` shim automatically. `scripts/cli.js` is built on `@mistralys/cli-menu`'s `createMenu()`, which turns a flat array of `{ id, key, label, category, description, run }` command descriptors into both an interactive keypress menu and a direct-dispatch CLI (`ai-insights <id> [flags]`). Every existing capability — persona sync, GUI launch, orchestrator runs, health checks — is added as one more entry in that array, delegating to a dedicated standalone script under `scripts/` via the library's `runScript()`/`runLongScript()` helpers (which spawn the child process with `stdio: 'inherit'` and forward its exit code). `@mistralys/cli-menu` also ships the raw-mode TTY primitives (`enterRawMode`, `restoreTerminal`, `isRawModeSupported`, `clearScreen`) that back every interactive list in this workspace, most directly the setup wizard's `runCheckboxMenu` keypress loop.

Claude Code personas are deployed as flat `.md` files with YAML frontmatter into `~/.claude/agents/` (path resolved cross-platform by the existing `getClaudeCodeAgentsDir()` in `scripts/publish-locations.js`) by `scripts/sync-personas.js`. That script already contains a private frontmatter parser (`parseFrontmatter()`) used for its own build-time validation, but it isn't exported for reuse elsewhere. Only the 9 ledger-suite personas carry a `role:` frontmatter field; none of the 34 standalone/ledger-support personas do — their only deployed identity is the machine `name:` slug (used for invocation) and a full-sentence `description:` (not label-shaped).

## Approach / Architecture

1. **Extract two small shared helpers** out of code that already implements the exact logic this feature needs, rather than re-implementing it:
   - `scripts/lib/frontmatter.js` — the frontmatter-block parser currently private to `scripts/sync-personas.js`, moved verbatim (no behavior change) and exported as `parseFrontmatter(filePath)`. Both `sync-personas.js` and the new launcher import it.
   - `scripts/lib/claude-cli.js` — the "is the `claude` CLI on PATH" predicate currently inlined inside `scripts/install-mcp-global.js`'s private `_checkClaudeCodeStatus()`, extracted as `isClaudeCliAvailable()`. Both `install-mcp-global.js` and the new launcher import it.
2. **New lib module `scripts/lib/launch-agent-core.js` + thin CLI script `scripts/launch-agent.js`** — the feature itself, split following this workspace's own established `scripts/lib/*.js` precedent (pure/testable logic *and* the picker I/O shell, all with no `main()`/CLI-invocation logic, alongside `scripts/lib/yaml-utils.js`, `scripts/lib/health-checks.js`, `scripts/lib/store-commands.js`, `scripts/lib/ledger-dirs.js`) rather than a single file gated by a run-guard:
   - `scripts/lib/launch-agent-core.js` (no `main()`, no process-wiring logic — importable by both the CLI script and its test file) exports:
     - Pure discovery/filtering: `discoverAgents(agentsDir)` (reads `~/.claude/agents/*.md`, applies the `role:` → filename-without-extension label rule, returns a sorted array) and `filterAgents(agents, query)` (case-insensitive substring match against label, invocation id, and description).
     - Pure picker-state reducer: `reducePickerInput(state, { str, key }, filteredLength)` — the same "separate the pure state transition from the raw-mode I/O loop" shape `@mistralys/cli-menu`'s own `runCheckboxMenu` uses internally, except exposed and independently unit-testable here (the library doesn't need to expose its own, since it has no filtering).
     - Picker I/O shells, extracted into this same module (cycle-2 rework — see Structural Improvements) rather than left in `scripts/launch-agent.js`, since one of them (`runNonInteractivePicker`) is a Test Plan obligation and importing it from a file whose `main()` runs unconditionally on import would trigger that `main()`'s real side effects during test collection: `runInteractivePicker(agents)` wires `process.stdin`'s `'keypress'` events (after `enterRawMode()`) to the reducer and redraws, and `runNonInteractivePicker(agents, initialQuery, { readlineFactory } = {})` is the `readline`-based fallback for non-TTY environments, mirroring the existing `askCleanInput()` pattern in `scripts/cli.js`, with an injectable `readlineFactory` seam for testing.
   - `scripts/launch-agent.js` — a genuinely thin CLI entry point that imports all five functions above from `scripts/lib/launch-agent-core.js` and contains only process wiring:
     - Launch: on selection, preflight-check `isClaudeCliAvailable()`, then `spawn('claude', ['--agent', id, ...passthroughArgs], { stdio: 'inherit' })`, forwarding the child's exit code.
     - `main()` dispatches to the imported `runInteractivePicker()`/`runNonInteractivePicker()` based on `isRawModeSupported()` and is invoked unconditionally at the bottom of the file — no run-guard is needed, since the file itself contains no logic that a test file needs to import directly (matching every other standalone script under `scripts/`, none of which uses a run-guard); all test-importable logic, including both picker functions, now lives in `scripts/lib/launch-agent-core.js`.
3. **Register `agent` as a new `ai-insights` subcommand** in `scripts/cli.js`'s existing commands array (category `Personas`, key `a`), delegating to `node scripts/launch-agent.js` via `runScript()` — the same one-line `cmdX` wrapper pattern every other command already uses. No new global binary, no new registration mechanism, no new `npm link` step for users who've already linked `ai-insights`.
4. **Document** the new command in the four places the workspace's own maintenance rules require for a new root-level script (`AGENTS.md`, `docs/references/menu-guide.md`, `docs/references/development.md`, `README.md`), plus a `ctx-generate` regeneration step so `CLAUDE.md` stays in sync.

## Rationale

Reusing the existing `ai-insights` binary (rather than adding a second global `bin` entry) was chosen because that exact question — "how do we expose a bare global command for this workspace" — was already researched and decided (`docs/agents/research/2026-05-29-developer-experience.md`, Tier 1 pattern), and a second bin entry would duplicate a solved problem while fragmenting the single documented entry point the README explicitly promises ("Everything runs through a single interactive menu"). Extracting the two shared helpers rather than re-implementing frontmatter parsing and CLI-availability detection avoids a second, silently-divergent copy of logic that already has known edge cases baked into it (the leading-HTML-comment tolerance in the frontmatter parser; the Windows `where` vs. `which` split in the CLI check). Building the picker directly on `@mistralys/cli-menu`'s raw-mode primitives — instead of adding a dependency like `inquirer`/`enquirer` — keeps the zero-third-party-interactive-prompt-library invariant this workspace has maintained everywhere else, and inherits that library's already-tested non-TTY safety guarantees for free.

`runNonInteractivePicker`'s stateful re-filter loop (accept a number to select, or free text to re-filter and reprint, looping until selection or empty-input cancellation) is a deliberately richer shape than this codebase's only existing non-interactive-fallback precedent, `askCleanInput` (`scripts/cli.js` L431–L436), which is a single one-shot `question()` with no loop. The loop is warranted here because `!isRawModeSupported()` does not only mean "CI or piped input" — it also covers a human typing at an interactive-but-non-raw-mode terminal (some SSH/tmux configurations fall into this category), where a single miss-typed or too-broad filter would otherwise force the user to re-invoke `ai-insights agent --filter <term>` from scratch instead of narrowing in place. For a genuinely non-interactive caller (CI, piped input), the loop still terminates in one iteration — a number or empty input on the first prompt behaves identically to the simpler one-shot shape, so the added statefulness costs nothing in that case while meaningfully improving the human-at-a-non-raw-terminal case AC-04 also has to cover.

## Pattern Alignment

- Follows the established `{id, key, label, category, description, run}` command-descriptor shape in `scripts/cli.js` (`Personas` category, alongside `sync-personas`, `package-personas`, `clean-agents`) — no departure.
- Follows the established `cmdX(args)` → `runScript()`/`runLongScript()` delegation pattern for wiring a standalone script into the CLI — no departure.
- Follows the established `scripts/lib/` location and single-responsibility-module shape for shared, testable, dependency-free helper logic (alongside `yaml-utils.js`, `ledger-dirs.js`, `health-checks.js`) — no departure.
- Follows the established "separate the pure state reducer from the raw-mode I/O loop" shape already used internally (but not exported) by `@mistralys/cli-menu`'s `runCheckboxMenu` — this plan makes that shape a first-class, independently-testable export of the new script rather than an unexported implementation detail, which is a deliberate strengthening (not a departure) given the new picker adds filtering the library's own menu doesn't have.
- Departs from `scripts/cli.js`'s `askCleanInput()` precedent by not extracting a shared "promisified readline question" helper even though the new non-interactive fallback needs an equivalent one-off. Justified: it is a five-line wrapper around `readline.createInterface(...).question(...)`, appearing at exactly two call sites total (the existing one and the new one) with no anticipated third; extracting it purely to avoid five duplicated lines adds an indirection with no growth trajectory to justify it (see Rationale/Justified Structure in Core Rules).

## Detailed Steps

1. **Extract `scripts/lib/frontmatter.js`.** Move `sync-personas.js`'s private `parseFrontmatter(filePath)` (L62–L80) into this new file verbatim, export it, and update `sync-personas.js` to `import { parseFrontmatter } from './lib/frontmatter.js'` in place of its local definition. No behavior change — same regex, same optional leading-HTML-comment handling, same return shape (`Object | null`).
2. **Extract `scripts/lib/claude-cli.js`.** Add an exported `isClaudeCliAvailable()` that runs the same `spawnSync(IS_WIN ? 'where' : 'which', ['claude'], { encoding: 'utf8', shell: false })` check currently inlined as the first branch of `install-mcp-global.js`'s private `_checkClaudeCodeStatus()` (L132–L148), returning a boolean. Update `_checkClaudeCodeStatus()` to call the new helper for that first branch instead of duplicating the `spawnSync` call inline; its `registered`/`stale` logic is unchanged.
3. **Create `scripts/lib/launch-agent-core.js`** with the following exported, independently-testable functions — no `main()`, no process-wiring/CLI-invocation logic, matching the established `scripts/lib/*.js` shape:
   - `discoverAgents(agentsDir)` — reads `.md` files in `agentsDir` (returns `[]` if the directory doesn't exist); for each file, calls `parseFrontmatter()`, derives `id = fields?.name || basename`, `label = fields?.role || basename` (the exact two-tier rule), `description = fields?.description || ''`; returns the array sorted by `label` (locale-aware `localeCompare`).
   - `filterAgents(agents, query)` — case-insensitive substring match against `label`, `id`, and `description`; empty/whitespace-only query returns the full list unfiltered.
   - `reducePickerInput(state, { str, key }, filteredLength)` — pure reducer: printable single-character input appends to `state.query` and resets `state.cursor` to `0`; `backspace` removes the last character and resets `cursor`; `up`/`down` move `cursor` clamped to `[0, filteredLength - 1]`; `return` yields `{ action: 'select' }` only when `filteredLength > 0`, else `{ action: null }`; `escape` or Ctrl+C yields `{ action: 'cancel' }`; everything else is a no-op.
   - `runInteractivePicker(agents)` — the raw-mode I/O loop: `enterRawMode()`, render the filter query line plus the current filtered/windowed list with the cursor row highlighted, listen on `process.stdin`'s `'keypress'` event, feed every event through `reducePickerInput()`, redraw on every state change, register a `SIGINT` handler that calls `restoreTerminal()` before re-raising (mirroring `runCheckboxMenu`'s own handler), and `restoreTerminal()` + resolve on `'select'`/`'cancel'`.
   - `runNonInteractivePicker(agents, initialQuery, { readlineFactory } = {})` — the `readline`-based fallback used when `!isRawModeSupported()`: prints a numbered, optionally pre-filtered list, then loops a single `question()` prompt accepting either a number (selects that row) or free text (re-filters and reprints); empty input cancels. `readlineFactory` defaults to `readline.createInterface` and is the injectable seam the Test Plan uses to drive this function with a stub interface (see Testing Strategy). `[added by: Plan Auditor, cycle 2]` This function (and `runInteractivePicker` above, for symmetry) is placed in this lib module — not in `scripts/launch-agent.js` alongside `main()` — specifically so that `scripts/tests/launch-agent.test.js` can import it without importing (and thereby executing) `main()`'s real side effects, which would occur on any import of `scripts/launch-agent.js` in an ES module context regardless of which named export the test destructures.
4. **Create `scripts/launch-agent.js`** as a thin CLI entry point importing all five functions above from `scripts/lib/launch-agent-core.js`, containing nothing but:
   - A `main()` entry point that: parses `--filter <term>` and any args after a bare `--` as passthrough args for `claude`; resolves `agentsDir` via `getClaudeCodeAgentsDir()` (imported from `./publish-locations.js`); calls `discoverAgents()`; if empty, prints a message pointing at `ai-insights sync-personas` and exits `1`; calls `isClaudeCliAvailable()` and exits `1` with a clear message if `false`; dispatches to the imported `runInteractivePicker()` or `runNonInteractivePicker()` based on `isRawModeSupported()`; on a `null` (cancelled) result prints "Cancelled." and exits `0`; on a selected id, `spawn('claude', ['--agent', id, ...passthroughArgs], { stdio: 'inherit' })` and exits with the child's exit code (mirroring the exit-code-forwarding shape already used by `install-mcp-global.js`'s shim and `cli-menu`'s own `runScript()`). `main()` is invoked unconditionally at the bottom of the file, with **no run-guard** — matching every other standalone script under `scripts/` (`sync-personas.js`, `install-mcp-global.js`, `backfill-duration.js`, `import-standalone.js`, `extract-dialogue.js`, `kill-orchestrator.js`, `read-log.js`, `build-skills.js`, `check-version-sync.js`, `extract-changelog-entry.js`, `generate-agents-overview.js`, none of which gate `main()` behind an invocation check). This is now unconditionally safe: the file contains no other exported logic — including the two picker functions, which cycle-2 rework relocated into `scripts/lib/launch-agent-core.js` — so no test file ever needs to import from `scripts/launch-agent.js` at all.
5. **Register the `agent` command in `scripts/cli.js`.** Add one entry to the existing commands array: `{ id: 'agent', key: 'a', label: 'Launch an agent', category: 'Personas', description: 'Pick a persona and launch it with Claude Code', helpVariants: [['agent --filter <term>', 'Pre-fill the filter query']], run: cmdAgent }`, with `cmdAgent(args)` defined alongside the other `cmdX` wrappers as `const code = runScript('node', [path.join(SCRIPTS_DIR, 'launch-agent.js'), ...args], { cwd: WORKSPACE_ROOT }); if (code !== 0) process.exit(code);` — the exact shape `cmdSyncPersonas` already uses.
6. **Add tests** per the Test Plan below.
7. **Update documentation** per Documentation Updates below, finishing with `node scripts/cli.js ctx-generate` so `CLAUDE.md` and `.context/` stay in sync with the `AGENTS.md` edit (never hand-edit `CLAUDE.md`).

- Modifying the persona build system (`@mistralys/persona-builder`, `scripts/build-personas.js`, or any `personas/*/src/meta/*.yaml`) to add a uniform pretty-label field across all three suites — the two-tier fallback rule the user specified already covers this without that larger change.
- Launching VS Code agent prompts or any target other than Claude Code's `--agent` flag.
- A `postinstall`-triggered or otherwise automatic global registration flow — the existing `npm link` step remains manual, matching current workspace conventions.
- Passing arbitrary `claude` flags beyond simple passthrough after a bare `--` (e.g. no dedicated flag-mapping layer).

## Acceptance Criteria

- AC-01: Running `ai-insights agent` (after `npm link`) from any directory opens an interactive, type-to-filter list of every persona deployed to `~/.claude/agents/`.
- AC-02: Each listed agent's display label is its `role:` frontmatter value when present (ledger-suite personas), otherwise its filename without the `.md` extension (standalone and ledger-support personas).
- AC-03: Typing narrows the visible list by case-insensitive substring match against the label, the underlying invocation id, and the description; arrow keys move the selection within the filtered list; Enter launches `claude --agent <id>` with the terminal handed over via `stdio: 'inherit'`; Escape or Ctrl+C cancels without launching anything.
- AC-04: When stdin is not a TTY (or raw mode is unsupported), the command falls back to a non-interactive numbered-list prompt instead of hanging or crashing.
- AC-05: If `~/.claude/agents/` is missing or empty, the command exits with a clear message pointing at `ai-insights sync-personas`, without throwing.
- AC-06: If the `claude` CLI is not found on `PATH`, the command exits with a clear message before attempting to spawn it.
- AC-07: `scripts/sync-personas.js` and `scripts/install-mcp-global.js` behave identically before and after the extraction refactor (existing test suites for both continue to pass unmodified).
- AC-08: `./menu.sh agent` (the repo-local invocation path, no `npm link` required) works identically to `ai-insights agent`.

## Testing Strategy

Unit-test every pure function in the new modules (`discoverAgents`, `filterAgents`, `reducePickerInput`, `parseFrontmatter`, `isClaudeCliAvailable`) in isolation using temp-directory fixtures, following the existing pattern in `scripts/tests/install-mcp.test.js` (real filesystem, temp dirs, no mocking). Because these pure functions now live in `scripts/lib/launch-agent-core.js` (see Structural Improvements — Major Finding 2 fix), the test file imports them directly with no run-guard or CLI-invocation workaround needed.

The raw-mode I/O loop `runInteractivePicker` — despite living in `scripts/lib/launch-agent-core.js` (cycle-2 rework, see Structural Improvements) rather than `scripts/launch-agent.js` — is intentionally left untested, consistent with this codebase's existing precedent of not unit-testing `@mistralys/cli-menu`'s own `runCheckboxMenu`/`showInteractiveMenu` keypress loops or `scripts/cli.js`'s `cmdCleanAgents` prompt loop: it has no meaningful branching of its own (all decision logic lives in the already-tested `reducePickerInput`), so its correctness is fully covered by the pure reducer/discovery functions it calls plus manual verification. Its relocation into the lib module is purely a testability-of-`runNonInteractivePicker` fix, not a signal that it has itself become a test obligation. `scripts/launch-agent.js`'s `main()` CLI entry point remains thin, untested glue, unchanged from cycle 1.

`runNonInteractivePicker` is **not** exempted under that same "thin glue" umbrella: unlike `runInteractivePicker` and `cmdCleanAgents` (a single one-shot prompt), `runNonInteractivePicker` owns real branching logic directly (number-vs-text dispatch, a re-filter loop, empty-input cancellation) that the Rationale section identifies as non-trivial and that AC-04 depends on. It is tested by driving it through a stub `readline.Interface`-shaped object passed as an injectable dependency (matching this codebase's temp-dir/real-fixture testing style rather than a mocking framework): the test constructs an object exposing `question(prompt, callback)` and `close()`, scripts a sequence of canned answers, and asserts the resulting selection/re-filter/cancel behavior against a small in-memory `agents` fixture. `runNonInteractivePicker(agents, initialQuery, { readlineFactory } = {})` accepts an optional `readlineFactory` override (defaulting to `readline.createInterface`) for exactly this seam — the same "accept the collaborator as a parameter with a real default" shape already used for `agentsDir` elsewhere in this plan, requiring no new dependency and no behavior change for production callers, which never pass the override. `[added by: Plan Auditor, cycle 2]` Because `runNonInteractivePicker` now lives in `scripts/lib/launch-agent-core.js` alongside the pure functions above, rather than in `scripts/launch-agent.js` next to the unconditionally-invoked `main()`, `scripts/tests/launch-agent.test.js` can import it directly with no risk of triggering `main()`'s real side effects — resolving the cycle-2 Critical finding.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **Raw-mode keypress handling behaves differently across terminal emulators (especially Windows Terminal vs. cmd.exe vs. PowerShell)** | Build entirely on `@mistralys/cli-menu`'s already-cross-platform-verified raw-mode primitives rather than hand-rolling ANSI/terminal handling; the library already documents and handles the `isRawModeSupported()` fallback path |
| **Extracting `parseFrontmatter()`/the CLI-availability check introduces a subtle regression in `sync-personas.js` or `install-mcp-global.js`** | Move the code verbatim (no logic changes) in step 1–2, and require both scripts' existing test coverage (`install-mcp.test.js`, persona frontmatter validation exercised by `build-personas.js --check`) to pass unmodified as AC-07 |
| **`claude` CLI not installed, or the selected agent's frontmatter `name:` doesn't match what `--agent` expects** | Pre-flight `isClaudeCliAvailable()` check before spawning (AC-06); the invocation id is read directly from the deployed frontmatter's own `name:` field, the same field Claude Code's `--agent` matcher already reads, so no separate mapping table can drift out of sync |
| **`~/.claude/agents/` empty or missing (personas never synced)** | Explicit empty-directory handling with a pointer to `ai-insights sync-personas` (AC-05) instead of an empty picker or a crash |

## Recommended Workflow
- **Workflow:** standalone
- **Rationale:** A single, well-understood module within existing conventions (new script + two small lib extractions + one CLI registration + docs), entirely within one code owner's session, with no cross-cutting architecture change or new external dependency — a full ledger pipeline (QA/security/review/release stages) would be disproportionate to the scope.
