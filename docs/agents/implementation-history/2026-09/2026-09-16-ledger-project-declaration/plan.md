## Prior Project Context

The repository's declared strategy has three horizons, and this work touches all of them. **Short term** ("as little friction as possible") is why the feature is delivered as two verbs on the already-linked `ai-insights` binary rather than as a new tool or dashboard action. **Long term** ("Personas First — all integrated tools exist only to support the personas") is the justification for the whole feature: the deliverable is not a file, it is the standalone Planner gaining strategic context it cannot otherwise reach. The same horizon's reliability goal (Windows/Linux/macOS) is why the consolidation in steps 2 and 12 matters — two divergent implementations of `.repositories.json` I/O is exactly the kind of thing that behaves differently on one platform and not another.

Four retrieved insights shaped the design: stateless storage helpers are plain-function modules (`f389f9ce`, applied in steps 3–5); generators must compare-before-write and be tested in temp directories (`d6f8fa4d`, steps 6 and the test plan); shared contracts belong at one execution choke-point (`d8e7dbeb`, the `syncProjectOutputs()` shape in step 6); and inline-shell pre-commit guards are a known weak spot (`2cd87f16`, which is why step 16 adds a single advisory line and nothing more).

## Summary

The ledger holds a three-horizon strategic vision per repository in `.repositories.json`, readable only through `ledger_get_repository_context` and therefore invisible to every non-ledger agent and developer. This plan introduces an opt-in, project-side `.ledger/` declaration folder containing a `settings.json`, and a generated, read-only mirror of the strategic vision written into that folder by a new `ai-insights ledger` command group. Configuration is a guided wizard — `ledger init` proposes the repository from the registry rather than asking the user to spell it out, and `ledger edit` reopens the same prompts with current values — layered over a flag-driven core that keeps every path scriptable. The wizard is reachable without typing a verb at all: the command group takes a key in the `ai-insights` interactive main menu, and a verbless invocation infers `init` or `edit` from whether the project already carries a declaration. The declaration doubles as an authoritative repository identity, replacing basename-derived `folder_names` matching where it is present. Writing into a consumer project is a new precedent for this codebase, so it is bounded by an explicit consent model — the ledger writes only inside `.ledger/` or into a path the project itself declared — enforced by a single sync choke-point and asserted by test. Along the way the plan consolidates the two divergent implementations of `.repositories.json` I/O onto the locked, schema-validated TypeScript one.

## Architectural Context

**Vision storage.** `StrategicVisionSchema` (`mcp-server/src/schema/repository-registry.ts` L12–L17) is three nullable strings on `RepositoryEntrySchema`; registry files live at `{storePath}/.repositories.json`, one per store, read by `loadRegistry()` and written by `saveRegistry()` under `withLock` + `atomicWriteJson`.

**Multi-store.** `StoreRouter` (`store-router.ts`) and `MultiStoreManager` (`multi-store-manager.ts`) collate across stores with store-order priority and first-match semantics; `store-context.ts` holds the process-wide singletons. The only by-id, all-stores lookup is `findEntryInStores()` — currently module-private inside `mcp-server/gui/api-repos.ts` (L125).

**Identity today.** `ledger_get_repository_context` (`repository-context.ts` L84–L120) fabricates a synthetic plan path from `cwd_path` solely to reuse `deriveRepoName()`, then matches the resulting basename against `folder_names`. `inferProjectRootFromPlanPath()` (`ledger-root.ts` L61–L100) is a pure, filesystem-free walk for a `docs/agents` anchor.

**CLI.** `package.json` exposes `bin: { "ai-insights": "./scripts/cli.js" }`, linked globally by `link-cli`. `scripts/cli.js` resolves `WORKSPACE_ROOT` from `import.meta.dirname`, so it is correct when invoked from any directory; `getOriginalCwd()` (`scripts/lib/original-cwd.js`) carries the user's real directory, and `cmdAgent` is its only current consumer. `scripts/lib/ledger-dirs.js` is the established bridge that loads compiled logic from `mcp-server/dist/` and rebuilds it when stale.

**Personas.** The ledger and standalone Planners share six `planner-*` partials; MCP-only content is gated with `{{#if has_mcp}}`. The Manifest Curator and AGENTS.md Curator each express ownership through a `## Scope Boundaries` table.

## Approach / Architecture

Five layers, each with one owner:

1. **Declaration schema** (`src/schema/project-declaration.ts`, new) — `ProjectSettingsSchema` (strict) and a locals variant. Pure shapes, no I/O.
2. **Declaration storage** (`src/storage/project-declaration.ts`, new) — filesystem discovery of the project root, loading, deep-merging the local override, and resolving output paths under a traversal guard. A plain-function module, per the `repository-registry.ts` pattern.
3. **Repository lookup** (`src/storage/repository-lookup.ts`, new) — `findEntryInStores()` relocated out of the GUI layer, so the GUI, the identity resolver and the CLI share one implementation with one documented first-match semantic.
4. **Output generation** (`src/outputs/`, new directory) — a pure renderer per output plus `syncProjectOutputs()`, the single choke-point that owns the write allowlist, the idempotence comparison, marker-guarded removal, and `--check`.
5. **Consumers** — the `ai-insights ledger` CLI group (`init` / `edit` / `sync`), the identity precedence inside `ledger_get_repository_context`, and the persona instructions that read the mirror.

The CLI group follows the core-plus-shells split the workspace already uses for `ai-insights agent`: a pure `scripts/lib/ledger-project-core.js` holding every decision, with two shells over it — a flag-driven non-interactive path and an interactive wizard. `init` and `edit` prompt when run on a TTY with inputs unsupplied, and are fully answerable by flags otherwise; `sync` is non-interactive in both modes, because a scheduled or hook-invoked regeneration must never block on a prompt. The group is additionally registered with a main-menu key, which is what makes it reachable from a bare `ai-insights` in a consumer project — and because the menu invokes a command with no arguments at all, the verbless entry point resolves `init` versus `edit` from the declaration state rather than asking the user which one they meant.

The CLI reaches layers 2–4 through a generalised `scripts/lib/ledger-bridge.js`, which subsumes today's `ledger-dirs.js` dist-loading mechanism. That bridge is also what resolves the duplication problem: `scripts/lib/store-commands.js` stops re-implementing `.repositories.json` and `stores.json` I/O and calls the compiled TypeScript instead.

Identity resolution becomes a single helper, `resolveRepositoryIdentity(cwdPath)`, with a three-step precedence — explicit argument, declared `repository_id`, folder-name derivation — and a hard failure when a declared id matches nothing, so a typo can never silently resolve to a different repository.

## Rationale

**Why a declaration file rather than a registry-side path field.** The registry knows `folder_names`, not filesystem locations, and one repository can be checked out many times. Consent to be written into has to live in the thing being written into; a store-side switch would let one machine's configuration cause writes on another.

**Why one sync choke-point.** The consent rule in D1 is only as good as its enforcement. A single function that computes the allowlist and performs every write makes the rule a testable invariant (AC-12) instead of a convention each new output must remember — the pattern insight `d8e7dbeb` records for shared contracts.

**Why a content hash rather than `last_modified`.** `RepositoryEntry.last_modified` changes when a label or `folder_names` entry is edited. Embedding it would rewrite a committed file on every unrelated registry edit and fail `--check` in CI for a change that did not touch the vision. Hashing only the three horizon strings makes staleness mean exactly what the file claims to mirror.

**Why the group is on the main menu, and why the verb is inferred.** The audience for `ledger init` is a developer standing in a consumer project with the globally linked binary on PATH, which is exactly the population that runs `ai-insights` bare and reads the menu rather than recalling a sub-verb. The `store` group is `key: null` because its audience is the workspace maintainer who already knows the verbs; this group's is not. Inferring the verb follows from the same observation: the menu calls `cmd.run([])` with no arguments, so a verbless entry point has to exist regardless, and the one piece of information it needs — is this project declared? — is already on disk and already read by `findProjectRoot()` + `loadProjectDeclaration()`. Asking the user to classify their own project would be asking them for a fact the tool holds. The explicit verbs keep their strict meanings, so nothing about inference weakens the guard rails: `ledger init` on a declared project still refuses without `--force`, and `ledger edit` on an undeclared one still errors.

**Why the configuration is a wizard.** The three inputs `init` needs — which repository, whether to enable the mirror, where it lands — are all ones the tool can propose better than the user can type. The repository is picked from the registry rather than spelled out, which removes the typo class AC-15 exists to catch before it can occur; the public-repository warning is shown immediately above the enable prompt rather than in a block of advisory output printed afterwards, where it is skimmed. The wizard is a shell over the flag-driven core, never a replacement for it, because `--dry-run`, scripted invocation and the acceptance criteria all need a non-interactive path — and because `scripts/lib/launch-agent-core.js` already establishes exactly this split for `ai-insights agent`.

**Why pull, not push.** Nothing in the ledger can locate a working tree. The CLI already runs from anywhere thanks to `npm link`, and `getOriginalCwd()` already exists to carry the invocation directory — the pull direction is the one the tooling supports today.

**Why the consolidation is in this plan rather than a follow-up.** The new CLI needs registry reads from a foreign cwd. Either it calls the compiled TypeScript, or it becomes the *third* implementation. Since the choice is forced, migrating the existing second implementation rides on work the plan is doing anyway, and it is the only moment this cleanup realistically gets funded. The marginal cost is not trivial, though, and the plan sizes it honestly: the compiled loaders are async, so nine of `store-commands.js`'s ten exported command functions change from synchronous to `async` (only `storeList` is already async), rippling into `cmdStore()`'s dispatch and the existing test suite's call sites (step 12b). That is a mechanical, fully-enumerated change rather than a design risk, but it is the larger half of step 12 and is budgeted as such.

## Pattern Alignment

- **Plain-function stateless storage modules** — `src/storage/project-declaration.ts`, `repository-lookup.ts` and `src/outputs/*` follow `src/storage/repository-registry.ts`; no classes are introduced (insight `f389f9ce`).
- **Dual-schema strictness** — `ProjectSettingsSchema` is strict input-style (`.strict()`, required `schema_version`), matching `constraints-storage.md` § "Dual-Schema Pattern". It is *not* given the permissive storage treatment, because the file is hand-authored rather than machine-migrated, and a broken opt-in must surface (§5.2 of the spec).
- **Loader failure contract — deliberate departure.** `loadRegistry()` swallows corruption and returns an empty registry. `loadProjectDeclaration()` instead returns a distinct `invalid` result that callers surface as an error. Justified: an absent registry is a normal first-run state, whereas a malformed declaration is always a mistake in a file the user wrote on purpose. The departure is recorded as a constraint in step 17.
- **Store-order first-match** — `findEntryInStores()` keeps its documented semantics verbatim when it moves, per `constraints-storage.md` § "Store-Order Priority Governs Write Routing".
- **CLI command group** — `ledger` mirrors `store`: one `COMMANDS` entry, `key: null`, `category: 'MCP Server'`, `helpVariants[]`, sub-verb dispatch on `args[0]`.
- **Invocation directory** — the new commands use `getOriginalCwd()`, following `cmdAgent`, and deliberately depart from the `{ cwd: WORKSPACE_ROOT }` used by every other command. `scripts/lib/original-cwd.js` documents this exact hazard; the departure is the point of the feature.
- **`--check` / `--dry-run` flags** — follows `build-personas.js --check` and `install-mcp-global.js --dry-run`.
- **Interactive core-plus-shells** — `scripts/lib/ledger-project-core.js` holds the pure decisions and `scripts/ledger-project.js` is a thin entry point, mirroring `scripts/lib/launch-agent-core.js` / `scripts/launch-agent.js`, including its non-TTY fallback obligation. Prompting reuses `askCleanInput()` (`scripts/cli.js` L452–L457) rather than introducing a prompt dependency.
- **Shared planner partials** — mirror instructions go into a shared partial, never duplicated into the two Planner twins.
- **Advisory pre-commit warnings** — the hook line follows the existing presentation-dist and `.context/` advisory blocks; it never blocks.
- **New pattern, justified: `src/outputs/`.** A new top-level directory in `mcp-server/src/` is introduced because generated project-side artefacts are neither storage (they live outside the ledger root) nor tools (no MCP surface). The `outputs` map in `settings.json` is its named growth trajectory; v1 ships exactly one member.

## Detailed Steps

1. **Declaration schema.** Add `mcp-server/src/schema/project-declaration.ts`: `ProjectSettingsSchema` — `schema_version` (literal `1`), `repository_id` (`z.string().regex(SLUG_REGEX)` from `schema/common.ts`), `outputs` (optional record keyed by a `z.enum` of known output ids, each `{ enabled: boolean (default false), path?: string }`), all `.strict()`. Add `ProjectSettingsLocalSchema` — the same shape with every field optional and `repository_id` omitted entirely. Export `OUTPUT_IDS` as the single list of valid output keys and `DEFAULT_OUTPUT_PATHS`.

2. **Shared lookup and bridge extraction.** (a) Create `mcp-server/src/storage/repository-lookup.ts` and move `findEntryInStores()` there verbatim, including its first-match documentation block; re-point `mcp-server/gui/api-repos.ts` at the new module. (b) Create `scripts/lib/ledger-bridge.js` by generalising `ledger-dirs.js`'s freshness guard and cached dynamic import into `loadDistModule(relativePath)`; re-implement `scripts/lib/ledger-dirs.js` as a thin re-export of `listAllProjectDirs` so its documented contract and callers are unchanged. (c) Add `listEntriesInStores(ledgerRoot)` to `repository-lookup.ts` as a sibling of `findEntryInStores()`, returning every registry entry across all stores with its owning `storePath`, deduped first-match in store order. It reproduces the by-id function's exact two-branch single/multi-store structure, so the two cannot drift on store semantics. It exists for the `init` wizard's repository picker (step 10b).

   2c. **Store-context bootstrap extraction.** Add `initStoreContext()` to `mcp-server/src/storage/store-context.ts`, containing the four-line sequence currently duplicated in `src/index.ts` (L116–L137) and `gui/server.ts` (L1458–L1461) — `loadStoresConfig()`, `new StoreRouter(config)`, `new MultiStoreManager(router)`, `setStoreContext(...)` — and re-point both processes at it. The CLI calls it once at the start of every `ledger` verb, through the bridge. **This is a correctness fix, not only a tidy-up:** `findEntryInStores()` guards on `isStoreContextInitialized()` and silently falls back to searching only `ledgerRoot` when the guard fails, so a CLI process that skipped the bootstrap would report a repository registered in a non-default store as unregistered — `init` would exit with AC-04's "not registered" message for a repository that plainly is. Both existing call sites keep their current behaviour; only the duplication is removed.

3. **Project-root detection.** Add `findProjectRoot(startPath)` to a new `mcp-server/src/storage/project-declaration.ts`: walk ancestors from `startPath` looking for `.ledger/settings.json` and return the nearest match, or `null` when the walk reaches the filesystem root without one. The walk is bounded by an explicit maximum depth. Keep `inferProjectRootFromPlanPath()` untouched — it stays pure; the filesystem probing lives only in the new function.

   `findProjectRoot()` has one contract for both consumers, with no plan-path fallback branch. An earlier draft of this plan gave it an opt-in `allowPlanPathFallback` flag on the premise that `resolveRepositoryIdentity()`'s `cwd_path` is typically plan-shaped; that premise is wrong, and the plan's own evidence says so. `GetRepositoryContextSchema` documents `cwd_path` as "the workspace root directory" (`repository-context.ts` L14–L21), and `inferProjectRootFromPlanPath()` resolves only when the supplied string *itself* already contains a `docs/agents` segment (`ledger-root.ts` L75–L92) — which a bare workspace root does not. The fallback would therefore have been inert for *both* consumers, not just the CLI. The `docs/agents` anchor is not dropped, though: it keeps serving the identity resolver's **derived** tier through the dedicated helper in step 3b, which is where it actually belongs. The `.ledger/` ancestor walk is strictly more capable than the string anchor for locating a *declared* root — it probes the filesystem and so resolves from a plan folder just as well as from a workspace root — so the declared tier loses nothing by dropping the branch.

   3b. **Derived-name helper.** Add `deriveRepoNameFromCwd(cwdPath)` to `mcp-server/src/utils/ledger-root.ts`, adjacent to `deriveRepoName()`: it appends the conventional `docs/agents/plans/synthetic-slug` anchor to `cwdPath` and delegates to `deriveRepoName()`. Because `inferProjectRootFromPlanPath()` matches the *first* `docs`+`agents` occurrence, appending is a no-op for an already plan-shaped path and supplies the missing anchor for a bare workspace root — so the helper is behaviour-identical to the synthetic-path expression it replaces (`repository-context.ts` L88–L96), for every input shape. This is the honest home for that construction: it is a documented, tested, named function on the module that owns the `docs/agents` convention, rather than a fabricated string literal inline in a tool handler. Pure — no filesystem access.

4. **Declaration loader.** In the same module add `loadProjectDeclaration(projectRoot)` returning a discriminated union — `{ kind: 'not_declared' }`, `{ kind: 'declared', settings, sourcePaths }`, `{ kind: 'invalid', errors[] }`. It reads `settings.json`, deep-merges `settings.local.json` over it, and rejects a local file that carries `repository_id` with a message naming the file (spec open question 4, resolved as load-time rejection so a stale local file explains itself). Unknown `schema_version`, unknown output keys and malformed JSON all produce `invalid`.

5. **Path resolution and atomic text writes.** (a) Add `resolveOutputPath(projectRoot, outputId, settings)` — defaults from `DEFAULT_OUTPUT_PATHS`, rejects absolute paths, rejects any path escaping `projectRoot` after normalisation, and rejects the three reserved `.ledger/` filenames (`settings.json`, `settings.local.json`, `README.md`). (b) In `mcp-server/src/storage/atomic-writer.ts`, extract the temp-then-rename core as `atomicWriteText(path, contents)` and make `atomicWriteJson()` delegate to it.

   10b. **`ledger init` — shells.** Add `scripts/ledger-project.js` implementing `init` against `getOriginalCwd()`, which it treats as the project root verbatim, performing no root detection at all, since `init` is the command that creates the marker the walk would look for. (y/N)` prompt that defaults to No; offer the default path with an override; show a summary of the exact files to be written and require a final confirmation; then offer to run `sync` at once when any output was enabled. Prompting uses `askCleanInput()` (`scripts/cli.js` L452–L457) — no new dependency.

The `AGENTS.md` and manifest routing lines and the `PreToolUse` hook snippet remain print-only in both shells, per the boundary in Out of Scope.

It writes `settings.json` only, never `settings.local.json`, and errors on a `not_declared` or `invalid` declaration pointing at `ledger init`.    10d. **Verb inference for the verbless entry point.** Add `chooseDefaultVerb({ projectRoot, cwd, declarationState })` to `scripts/lib/ledger-project-core.js` — a pure function over the result of `findProjectRoot()` (step 3) and `loadProjectDeclaration()` (step 4), performing no I/O of its own. It returns one of: `{ verb: 'init', projectRoot: cwd }` when no ancestor carries a declaration; `{ verb: 'edit', projectRoot, confirmRoot: false }` when the declaration is valid and `projectRoot === cwd`; `{ verb: 'edit', projectRoot, confirmRoot: true }` when the valid declaration lives in an *ancestor* of the cwd, so the shell confirms the resolved root and offers `init` here instead before editing something the user may not have meant; and `{ error: 'invalid_declaration', projectRoot }` when a declaration exists but fails schema validation — a broken `settings.json` is repaired or re-created deliberately, never silently overwritten by an inferred `edit`. Two consequences follow from the library's menu contract and must be implemented here, not assumed:

   - The menu calls `cmd.run([])` with **no arguments**, so `cmdLedger([])` must take the inference path from step 10d rather than printing usage. The same branch serves a bare `ai-insights ledger` on the command line, so menu and CLI cannot diverge.
   - When `run` returns a Promise the menu does **not** wait for a keypress before redrawing, which would wipe the wizard's summary off the screen. `cmdLedger` therefore ends with `await waitForKey()` on the interactive path only — TTY, no flags — following `cmdInstallMcp` and `cmdLinkCli`. It must never do so for `sync`, `--check`, or any flag-driven invocation, which would hang the pre-commit hook. Keep every exported name, parameter list and return shape — including the `configPath` and `_storesDirOverride` test hooks — so no caller's arguments change.

   **This is not a drop-in I/O swap: the sync/async contract changes.** The compiled `loadRegistry`/`saveRegistry` are `async` (file lock + `atomicWriteJson`), and the bridge reaches them through a dynamic `import()`, which cannot be awaited from a synchronous function. The module exports ten command functions, nine of which are currently declared non-async — `storeInit`, `storeAdd`, `storeRemove`, `storeSetDefault`, `storeRepoAdd`, `storeRepoMove`, `storeRepoList`, `storeConflicts`, `storeStatus` (only `storeList` is already `async`) — and all nine must become `async`, along with the exported I/O helpers `loadRegistry`, `saveRegistry`, `loadConfig` and `saveConfig`. The ripple reaches two caller sets that must be updated in the same step:

   - `cmdStore()` in `scripts/cli.js` (L682) is **already** declared `async` and already awaits `storeList()` at its one existing async call site (L733), so the function signature does not change. The edit is adding `await` to the other nine command-function call expressions inside its `switch`, so each sub-verb's exit code is read from the resolved result rather than from a pending promise.
   - `scripts/tests/store-commands.test.js` must `await` each call site. That test file therefore does *not* pass literally unchanged — its assertions and fixtures stay as they are, but its call expressions gain `await`; see the Testing Strategy for the true reach of that edit.

## Assumptions

- The `ai-insights` binary is globally linked on machines that will run `ledger init` / `ledger sync`; the existing `global-cli-linked` health check covers the failure mode.
- `mcp-server/dist/` is reachable and buildable from the linked checkout, which is what makes the bridge viable from a foreign cwd — the same assumption `scripts/lib/ledger-dirs.js` already makes.
- Consumer projects are willing to commit the generated mirror (D7); projects that are not simply leave the output disabled.
- Only one output ships; the `outputs` map's shape is designed for more but nothing else is added in v1.

## Constraints

- The ledger writes into a project only inside `.ledger/` or a declared output path (D1) — enforced at the sync choke-point and asserted by test.
- No MCP tool gains a `store_id` parameter (`constraints-storage.md` § "Multi-Store Routing Requires No New Tool Parameters"); the CLI's `--repository-id` is the sanctioned user-facing exception.
- All new root-script code is cross-platform Node with `path.join`/`path.resolve` and no Unix-only utilities.
- Tests run against temp directories with isolated ledger roots, never the live workspace (`constraints-testing.md`; insight `d6f8fa4d`).
- Generated persona outputs are never edited; only suite sources are touched, and `build-personas.js --check` gates the commit.
- No `.refine()`/`.transform()`/`.superRefine()` on outer tool schemas — path validation lives in loader code.

## Out of Scope

- Any second generated output beyond `strategic-vision`.
- An MCP tool that lets an agent trigger a sync (spec open question 7). The argument against v1: it would hand every agent a write path into the working tree in exchange for saving one CLI call the user can already run, and the consent model's value comes precisely from writes being rare and explicit. Revisit only if a concrete agent workflow is blocked by the CLI hop.
- Pushing regeneration from the dashboard Strategy page.
- Dashboard UI changes, including a "declared via `.ledger/`" indicator.
- Adopting the new identity precedence in `project-resolver.ts` and `project-lifecycle.ts`.
- The ledger writing to `AGENTS.md`, the project manifest or `.claude/settings.json` in consumer projects — the CLI prints, the user or the owning curator applies. The single carve-out is the `/.ledger/settings.local.json` gitignore line, which the `init` wizard offers to append on explicit confirmation: it is one idempotent append to a file no curator owns, and omitting it is what leaks a machine-local file.
- Refactoring `.githooks/pre-commit` into a guard registry.

## Testing Strategy

Four layers. **Pure functions** (`visionHash`, `renderStrategicVision`, `parseGeneratedHeader`, `resolveOutputPath`) are tested as pure input/output with no filesystem. **Filesystem units** (`findProjectRoot`, `loadProjectDeclaration`, `syncProjectOutputs`) run against `mkdtemp` trees that mirror only the directory shape under test, per `constraints-testing.md` and insight `d6f8fa4d` — never the live workspace. **Tool-level integration** exercises `ledger_get_repository_context` with an isolated ledger root and a synthetic declared project, covering the identity precedence and the `mirror` field. **CLI tests** (Vitest, `scripts/tests/`) split in two, following the `launch-agent-core.js` precedent: the decision core (`ledger-project-core.js`) is tested as pure functions with no prompting and no spawning, which is where the `init`/`edit` acceptance criteria are actually asserted; the shells are then tested by spawning the command against a temp project root with an injected config path, asserting exit codes and printed status lines rather than internals. The wizard shell is driven by feeding a scripted sequence to an injected reader, and its equivalence to the flag-driven path is asserted on the resulting file bytes (AC-27) rather than on transcript text, so prompt wording can change without breaking the suite. The consent invariant (AC-13) is tested by asserting on the write set `syncProjectOutputs()` produces, not by scanning the filesystem afterwards, so it fails loudly when a future output forgets the allowlist. Regression protection for the two relocations (steps 2a, 12b) comes from the existing `mcp-server/tests/gui/` and `scripts/tests/store-commands.test.js` suites still passing. The GUI suite runs literally unchanged. The store-commands suite keeps every assertion and fixture but gains `await` at its call sites — and that edit reaches **nearly every `it()` block in the file**, not only the ones exercising the nine converted command functions: step 12b also converts the exported helpers `loadConfig` and `loadRegistry`, which the existing tests call synchronously inside assertions throughout (e.g. `const config = loadConfig(configPath)` at L72). So essentially every callback in the file becomes `async` and every `loadConfig`/`loadRegistry`/command call gains `await`. A reviewer verifying "no other edit" against the diff should expect a file-wide, mechanically uniform change, not a handful of touched blocks. The edit is itself part of the regression evidence, since an unawaited call surfaces immediately as a failed post-command file-state assertion — or, for the helpers, as an assertion against a `Promise` rather than a config object.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **Writing into a consumer repository is a new precedent and a mistake here damages a user's working tree** | Every write goes through one function that computes and asserts the allowlist; AC-13 tests the write set directly; unmarked files are never removed; the recommended `PreToolUse` hook denies agent writes into `.ledger/` independently |
| **The generated file churns in Git, producing noise in every unrelated commit** | Staleness and equality are decided on a hash of the three horizon strings only; `generated-at` never triggers a rewrite; AC-06 and AC-07 lock the behaviour in |
| **Migrating `store-commands.js` to the compiled bridge breaks the `store` command group** | Every exported name, parameter list and test hook is preserved; `scripts/tests/store-commands.test.js` runs as the regression gate with only `await` and `async` callbacks added, file-wide (AC-22); the migration is a separate step that can be reverted without touching the new feature |
| **The sync→async conversion of `store-commands.js` silently drops an unawaited promise, so a `store` command reports success before its write lands** | Step 12b names all nine command functions and all four I/O helpers that change contract, plus both caller sets (`cmdStore()`'s nine unawaited dispatches in `scripts/cli.js`, the existing test suite); the regression gate asserts exit codes and post-command file state, so a lost `await` surfaces as a failed assertion rather than a flaky write; `cmdStore()` — already `async` — reads each sub-verb's exit code from the resolved result |
| **`mcp-server/dist/` is stale or unbuildable when the CLI runs from a foreign project** | The bridge inherits `ledger-dirs.js`'s freshness guard and rebuilds on demand, exiting with a clear message on build failure — the behaviour `import-standalone.js` already relies on |
| **A hidden `.ledger/` is invisible to agents, so the mirror is written and never read** | Verified during research that ripgrep skips hidden directories by default; routing lines in `AGENTS.md` and the manifest are mandatory for declared projects, and both curators audit for them (AC-24) |
| **Verb inference picks `edit` on an ancestor project when the user meant to declare the directory they are standing in** | `chooseDefaultVerb()` returns `confirmRoot: true` whenever the resolved root differs from the cwd; the shell prints the resolved root and offers `init` here instead before any prompt that could write (AC-35). The explicit `ledger init` never walks upward at all (step 10b). |
| **Inferred `edit` silently rewrites a declaration that failed validation, destroying fields the user was mid-way through hand-editing** | `chooseDefaultVerb()` returns `invalid_declaration` rather than a verb; the shell errors naming the file and starts no wizard (AC-35) |
| **The menu redraw wipes the wizard's summary, so the user never sees what was written** | `cmdLedger` awaits a keypress on the interactive path, matching `cmdInstallMcp` and `cmdLinkCli`; AC-36 asserts both that it waits interactively and that it does not for `sync`, where waiting would hang the hook |
| **A future command claims the same menu key and silently shadows the `ledger` entry** (the library's keymap is first-registration-wins, with no collision error) | AC-34 is asserted against the whole `COMMANDS` array in `scripts/tests/cli-commands.test.js`, so the collision fails a test rather than disappearing from the menu |
| **An interactive prompt hangs a scripted or hook-driven invocation** | `sync` never prompts in any mode; `init`/`edit` prompt only on a TTY with inputs unsupplied, and otherwise exit non-zero naming the missing flag (AC-28), with the test asserting under a timeout that would expire on a hang |
| **The wizard and the flag path drift, so the documented flags stop producing what the prompts produce** | Both are shells over one decision core; AC-27 asserts byte-identical `settings.json` from equivalent inputs, and the acceptance criteria are tested against the core rather than through prompt transcripts |
| **The CLI reads registry state without an initialised store context and reports a registered repository as unregistered** | Step 2c extracts `initStoreContext()` and every `ledger` verb calls it; AC-33 pins the multi-store resolution, and the store-context test pins the silent single-store degradation that made this failure invisible |
| **`edit` rewrites `settings.json` and drops something the user hand-authored** | `ProjectSettingsSchema` is `.strict()`, so there are no unmodelled fields to lose; the generated file carries no comments by design; `edit` writes `settings.json` only and never touches `settings.local.json` (AC-31) |
| **A declared `repository_id` silently binds a project to the wrong repository** | Hard error naming the id and every store searched, with no folder-name fallback (AC-15) |
| **Vision content leaks into a public repository** | All outputs default to off (D5); `ledger init` prints an explicit warning before anyone enables one; the file is only written by a deliberate CLI run |
| **Persona edits land without a rebuild and break the blocking pre-commit check** | `build-personas.js --check` is already blocking; step 17 makes the rebuild and the `--check` runs explicit release obligations (AC-26) |
