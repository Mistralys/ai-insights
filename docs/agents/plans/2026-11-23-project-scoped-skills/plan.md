## Summary

Give every skill in `skills/` a declared publish scope. A `scope` field in `skills/meta/{slug}.yaml` takes `local` (this AI Insights repository only) or `global` (the user home directories, as today), and defaults to `local` when omitted. Local skills are published into this repository's `.github/skills/{slug}/SKILL.md` (VS Code / Copilot) and `.claude/skills/{slug}/SKILL.md` (Claude Code); global skills keep going to `~/.copilot/skills/` and `~/.claude/skills/`. The local output becomes a tracked generated artefact with a freshness check. The hand-maintained `.github/skills/release-check/SKILL.md` and the two VS Code prompt files `.github/prompts/changelog.prompt.md` and `.github/prompts/changelog-archive.prompt.md` move into the skills build as the skills `release-check`, `insights-changelog` and `insights-changelog-archive`; the prompt files are deleted and every reference to them is updated. `insights-pr-review`, which is written for use in other repositories, is set to `global` scope; every other skill is set to `local` scope.

The existing `sync-personas` CLI command, which keeps the menu's `p` hotkey, becomes the single **publish** action for personas and skills. Without a `--parts` flag in an interactive terminal it first shows a checkbox submenu — `Personas ({N})`, `Skills - Global ({N})`, `Skills - Local ({N})` — with every part selected on first use and the last confirmed selection remembered per checkout; only the selected parts are published, and an empty selection publishes nothing. In a non-interactive shell without `--parts`, every part is published. `--parts` restricts the parts in either mode, so `sync-personas --parts personas` is the former personas-only behaviour, and every existing caller that means "personas only" is switched to it. The counts come from the same sources the build and publish read. The checkbox UI is a new public prompt in the sibling `cli-menu` library, generalised from its existing internal setup checkbox, so this plan spans two repositories.

## Architectural Context

- **Sources:** `skills/meta/{slug}.yaml` (metadata) + `skills/src/{slug}.md` (content), shared defaults in `skills/meta/_shared.yaml`. Documented in `skills/README.md`.
- **Build:** `scripts/build-skills.js` drives `@mistralys/persona-builder` (`build()` with a private `TargetRegistry` holding `vscode-skill` and `claude-skill` targets; frontmatter templates are inline constants; context flags `target_vscode_skill` / `target_claude_skill`). Output: `dist/vscode-skills/{slug}.md`, `dist/claude-skills/{slug}.md` (gitignored). The library merges every YAML key into the template context and does not warn about unknown keys, even with `strict: true` (verified empirically against v3.0.1), so a new `scope` key needs no change in the `ai-persona-builder` repository.
- **Publish:** `scripts/publish-skills.js` is a monolithic script that copies every dist file to `~/.copilot/skills/{slug}/SKILL.md` and `~/.claude/skills/{slug}/SKILL.md` via `getVSCodeSkillsDir()` / `getClaudeCodeSkillsDir()` from `scripts/publish-locations.js` (home-relative segments from `shared/publish-locations.json`, also read by the MCP server).
- **CLI:** `scripts/cli.js` → `cmdBuildSkills`, `cmdPublishSkills` (build, then publish with only `--dry-run` forwarded), `cmdBuildMaintain` (no skills step). The `p` hotkey is the `sync-personas` command (label "Sync personas", `cmdSyncPersonas` → `scripts/sync-personas.js` with all args); `build-skills` and `publish-skills` are keyless commands. The `personas` setup component calls `scripts/sync-personas.js` directly through `spawnSync`, not through the command. `cli.js` calls `createMenu(...).run(...)` at module top level, so its `cmd*` functions are not importable and are tested by source-text assertions (`scripts/tests/cli-cmd-agent.test.js`).
- **Callers of the `sync-personas` command:** the `personas-fresh` health-check fix hint (`scripts/lib/health-checks.js` L283, display only), the empty-agents message in `scripts/launch-agent.js` L68, and documentation (`docs/references/menu-guide.md`, `docs/references/development.md`, `docs/references/persona-quickstart-ide.md`, `skills/README.md`). CI, `package.json` and `menu.sh` do not call it. Many documents cite the `scripts/sync-personas.js` script, whose behaviour stays personas-only.
- **Menu library:** `@mistralys/cli-menu` `^1.1.0` (installed from npm; source in the sibling `cli-menu` repository). A hotkey runs `cmd.run([])` with no flags; a direct command receives every argument after the command name; an async command is awaited without a "press any key" pause. The library has a raw-mode checkbox TUI, `runCheckboxMenu` in `cli-menu/src/setup/checkbox-menu.ts`, but it is internal (not exported) and hardwired to setup components (title, `detect()`-based pre-checks, `(done)` tag). Raw-mode primitives (`isRawModeSupported`, `enterRawMode`, `restoreTerminal`) and `waitForKey` are exported. The library has no persisted-state facility.
- **Persona discovery:** `scripts/lib/name-mapping.js` `generateNameMapping()` discovers persona metadata inline (ledger `/^\d+-.*\.yaml$/`, other suites non-`_` `.yaml`); 44 personas today, equal to the `personas/name-mapping.json` entry count.
- **Legacy:** `scripts/sync-personas.js` → `syncSkills()` copies flat `*.md` files from `<repo>/.claude/skills/` into `~/.claude/skills/` during a Claude Code persona sync. `.claude/skills/` has never existed, so it is dead code today and would push local skills into the global home once it does.
- **Tracked state today:** `.github/skills/insights-audit-persona/SKILL.md` (a committed copy of the VS Code build output) and `.github/skills/release-check/SKILL.md` (hand-written) are tracked; nothing under `.claude/` is tracked; `.claude/agent-memory/` is the only ignored `.claude` path.
- **Generated-artefact rules:** `docs/agents/project-manifest/generated-artefacts.md` (tracked artefacts need a row with discard verdicts), the Standing Decision on feature branches, and the default-branch build-first rule (`node scripts/cli.js build-maintain`).

## Approach / Architecture

1. **Scope lives in metadata and is resolved by one module.** A new `scripts/lib/skill-catalog.js` reads `skills/meta/*.yaml` (skipping `_`-prefixed files) with `parseYamlScalars()`, and returns one entry per skill: `{ slug, name, scope, agent }`. It owns `SKILL_SCOPES = ['local', 'global']` and `DEFAULT_SKILL_SCOPE = 'local'`, and reports errors (scope value not in `SKILL_SCOPES`, with a message naming the file, the value and the valid values `local` and `global`; `name` not equal to the file stem; missing `skills/src/{slug}.md`) and warnings (an `agent` slug that no persona in `personas/name-mapping.json` carries as `claude_code.agent_name`; the warning is skipped with a note when `name-mapping.json` is absent). The persona builder never sees the scope as anything but an ignored key.
2. **Locations stay in `publish-locations.js`.** It gains `getLocalVSCodeSkillsDir(repoRoot)` → `<repoRoot>/.github/skills`, `getLocalClaudeCodeSkillsDir(repoRoot)` → `<repoRoot>/.claude/skills`, and `getSkillTargetDirs(scope, repoRoot)` → `{ vscode, claude }` for either scope. Local locations are repo-relative constants in the JS module and are not added to `shared/publish-locations.json`, which is home-relative and shared with the MCP server, which has no use for them.
3. **Publish is split into a planner and a thin CLI.** A new `scripts/lib/skill-publish.js` exports:
   - `planSkillDeployments({ builtFiles, catalog, repoRoot, scopeFilter, homeDirs })` → a list of `{ slug, ide, scope, destDir, destFile, content }`. A built stem with no catalog entry is an error ("rebuild: no metadata for built skill").
   - `checkSkillDeployments(plan, { repoRoot, catalog })` → stale, missing and orphaned local-scope files. It is used by `--check` and only ever reads.
   - `applySkillDeployments(plan, { dryRun })` → today's per-stem clear-and-write behaviour.
   - `findLocalOrphans(catalog, repoRoot)`: directories under the two local skill roots whose `SKILL.md` carries the generated marker (point 4) and whose slug is no longer a local-scope skill. The real publish removes them; `--check` reports them.
   - `findShadowedSkills(catalog, homeDirs)`: local-scope slugs that also exist in a global skill directory. The publish prints a warning and never deletes, because a global copy may belong to another checkout or to the user. Global-scope slugs are never reported: their home copy is the intended deployment (today `insights-pr-review`).

   `scripts/publish-skills.js` becomes a CLI over these functions with `--dry-run`, `--check` (local scope only; exit 1 when anything is stale, missing or orphaned) and `--scope local|global|all` (default `all`). A scope that holds no skills is not an error: the CLI logs that the scope is empty and exits 0, because the publish action (point 7) may select a part whose count is 0.
4. **Generated marker.** Both frontmatter templates in `scripts/build-skills.js` emit an HTML comment directly after the closing `---`: `<!-- Generated from skills/src/{{name}}.md by scripts/build-skills.js. Edit the source, then run: node scripts/cli.js publish-skills -->`. It tells agents and humans that the tracked output is generated, and it is the ownership proof orphan cleanup relies on. Where the library's frontmatter/content join does not place the line as intended, the implementer may inject the same marker in `planSkillDeployments` instead; the acceptance criteria test the deployed file, not the mechanism.
5. **Local output is tracked.** `.github/skills/{slug}/SKILL.md` and `.claude/skills/{slug}/SKILL.md` for local-scope skills are committed generated artefacts, classified as runtime-coupled in `generated-artefacts.md` because the IDEs load them. Build & Maintain regenerates them (build plus `publish-skills --scope local`), CI checks them (`publish-skills --check`), and the feature-branch rules apply unchanged: drift is not committed, and a branch that changed a skill source commits the regenerated output with it.
6. **Adoption and conversion.** `release-check`, `insights-changelog` and `insights-changelog-archive` become ordinary local-scope skills in `skills/`. The changelog skills delegate to the Changelog Curator: on Claude Code through `context: fork` + `agent: changelog-curator`; on VS Code, which has no `agent` frontmatter, through a `{{#if target_vscode_skill}}` block in the content that tells the active agent to hand the task to the **Changelog Curator** agent as a sub-agent, or to carry it out itself if it already is that agent. The old files are deleted, not redirected.
7. **`sync-personas` becomes the publish action with a part selector.**
   - **Library (`cli-menu`).** A new public `runCheckboxPrompt(options)` in a new `cli-menu/src/prompts/checkbox-prompt.ts` (engine layer), exported through the barrel with its types `CheckboxPromptItem` (`id`, `label`, optional `desc`, optional `checked`, optional `tag`) and `CheckboxPromptOptions` (`title`, `items`, optional `instructions`). It keeps the existing key bindings and SIGINT handling, returns the checked ids in item order on Enter (an empty array when nothing is checked), `null` on `q` and in a non-TTY. A pure `reduceCheckboxInput(state, input)` and `buildCheckboxLines(state, options)` carry the logic so it is testable without a terminal. The internal `runCheckboxMenu` becomes a thin adapter over it (title "Select components to set up:", `checked` from `detect()`, `tag: '(done)'`), so the library keeps a single checkbox implementation. The library stays free of state persistence: remembering a selection is the consumer's concern.
   - **Workspace logic (`scripts/lib/publish-parts.js`, new).** A frozen `PUBLISH_PARTS` registry in display order — `personas` ("Personas", deployed by `scripts/sync-personas.js`), `skills-global` ("Skills - Global", `skillScope: 'global'`), `skills-local` ("Skills - Local", `skillScope: 'local'`) — each with a short `desc` naming its destinations. Around it: `countPublishParts({ personasDir, skillsDir, nameMappingPath })` (personas from `listPersonaMetaFiles()`, skills from `loadSkillCatalog()` by scope, so the counts match what the build and publish would process); `formatPartLabel(part, count)` → `Personas (44)`; `parsePartsArg(args)` (`--parts <id,id,…|all>`); `skillScopeForParts(ids)` → `all` / `global` / `local` / `null`; `loadPublishSelection(statePath)` / `savePublishSelection(statePath, ids)`; `resolvePublishSelection({ args, isTTY, prompt, statePath, counts })`; and `planPublishRun(ids, args)` → the ordered list of `{ script, args }` invocations.
   - **Command (`scripts/cli.js`).** The existing `sync-personas` command keeps its id and the `p` hotkey; its label becomes "Publish personas & skills" and its `run` function, `cmdSyncPersonas`, is rewritten as the publish action. No new command id is added. `cmdSyncPersonas` resolves the selection, executes the planned invocations in order (personas first through `scripts/sync-personas.js`, then one skills build and one `publish-skills --scope <mapped>`), stops at the first failing script like the other commands, and calls `waitForKey()` when the submenu was shown (the menu does not pause after an async command). The `scripts/sync-personas.js` script is unchanged in purpose: it deploys personas only, and it is what the Personas part runs.
   - **Existing callers.** Callers whose intent is personas only are switched to `sync-personas --parts personas`, which runs exactly what the command ran before: the `personas-fresh` fix hint in `scripts/lib/health-checks.js` and the empty-agents message in `scripts/launch-agent.js` (`ai-insights sync-personas --parts personas`, or `./menu.sh sync-personas --parts personas`), plus the documents listed in Documentation Updates. Callers that cite the `scripts/sync-personas.js` script need no change. The `personas` setup component keeps calling the script directly.
   - **Selection rules.** With `--parts`, the flag decides in a TTY and a non-TTY alike, no submenu is shown, and the stored selection is neither read nor written. Without `--parts` in a TTY (hotkey or direct command), the submenu opens pre-checked from the stored selection, or with every part checked on first use or when the stored file is missing, unreadable or holds no known id. Without `--parts` in a non-TTY (agents, CI, piped input), every part is published and the stored selection is ignored, so agent runs never depend on hidden local state. Confirming with at least one part saves the selection; confirming with none, or cancelling with `q`, publishes nothing, prints "Nothing selected — nothing published." (or "Cancelled"), leaves the stored selection unchanged and returns normally.
   - **Storage.** `<repo>/.cli-state.json` (new, gitignored), a per-checkout JSON object keyed by feature: `{ "publish": { "parts": ["personas", "skills-global", "skills-local"] } }`. Saving rewrites only the `publish` key and preserves any other key.
   - **Flag mapping.** `--parts skills-local` ≡ `publish-skills --scope local`, `--parts skills-global` ≡ `--scope global`, both ≡ `--scope all`. `--dry-run` is forwarded to every selected part (sync, build, publish); `--target` and `--custom-path` go to the personas part only (skills always deploy to both IDEs); `--strict` goes to the skills build only. An empty or unknown `--parts` value exits 1 naming the valid ids.

## Rationale

- **Default `local`:** all skills but one are bound to this repository, and a default that writes into the user's home directory is the riskier one to get by accident. Making a skill global is then an explicit, reviewable opt-in, as `insights-pr-review` now shows. The field is still written explicitly on every current skill, so the default only governs future omissions.
- **The word "local":** decided by the user (Resolved Questions 6). It matches the submenu's "Skills - Local" row and the `skills-local` part id, so the YAML value, the `--scope` value and the part id use one word, and `--parts skills-local` maps onto `--scope local` without translation.
- **`insights-pr-review` global:** decided by the user (Resolved Questions 1). Its content already supports cross-repository use, so only its metadata changes; its deployment destinations are the same home directories as today.
- **Scope resolved from source metadata at publish time, not from build output:** the scope is not part of the built content, so reading it at publish time cannot disagree with what was built. A built stem without metadata is reported as an error, which catches a stale `dist/`.
- **Planner/CLI split:** the current script can only be tested as a subprocess against the real home directories. Pure planning and checking functions with injectable roots make every routing rule unit-testable in temporary directories, and give `--check` and the real publish one shared code path.
- **Tracked over ignored:** a fresh clone gets its local skills immediately (strategic short-term goal), GitHub-hosted Copilot sessions see `.github/skills/`, and the two files already tracked under `.github/skills/` stay tracked instead of being untracked. The cost, generated output in version control, is handled by the existing generated-artefact rules plus the new CI freshness check.
- **Orphan cleanup only with the marker, only in local scope:** the marker proves the directory was generated. Global directories are shared by every checkout (STABLE, DEV) and by the user, so publish never deletes there; it only warns about shadowing.
- **Removing `syncSkills`:** keeping it would leave a second, unscoped route from `.claude/skills/` into `~/.claude/skills/`, the exact opposite of local scope.
- **Checkbox prompt in the library, not in this repository:** decided by the user (Resolved Questions 3). A checkbox selector is exactly the library's domain, it already has one, and generalising it removes the need for a second raw-mode implementation here. A local copy would duplicate the keypress loop and the mandatory SIGINT cleanup. Consumers: the publish action now; `cmdCleanAgents`' numbered location prompt is the next candidate (left for a later plan); the library's own setup wizard through the adapter. The cost is a library release before this repository's change can be merged (Human Actions 4–5).
- **Repurposing `sync-personas` instead of adding a `publish` command:** decided by the user (Resolved Questions 4). The `p` hotkey and the command name people already type keep working and now do the broader job. The cost is that the command's default changes from "personas" to "everything"; it is contained by switching every caller that means personas only to `--parts personas` in the same change, and by the interactive submenu, which shows what will run before anything runs. The `scripts/sync-personas.js` script keeps its personas-only meaning, so the many documents that cite the script stay correct.
- **Per-checkout selection storage:** decided by the user (Resolved Questions 7). The Skills - Local part is per checkout by definition, and a DEV checkout typically wants a different selection from STABLE (for example, not overwriting the globally deployed personas the live workflow uses). `~/.ai-insights/` would share one selection across checkouts. The repo-root gitignored file follows the `.orchestrator-run.json` precedent.
- **Non-TTY publishes everything without `--parts`:** decided by the user (Resolved Questions 5). An agent's run must not depend on a selection someone made interactively on that machine; "all" matches the submenu's first-use default and `publish-skills`' `--scope all` default.
- **`--target` stays personas-only:** `scripts/sync-personas.js` owns `--target` and `--custom-path`; `publish-skills.js` has no IDE filter, and adding one is outside the requested behaviour. Restricting the whole run to one IDE is therefore done with `--parts personas --target vscode`; the help text and menu guide state it.
- **Empty selection is a no-op, not an error, and is not saved:** pressing Enter with nothing checked is a deliberate "never mind"; saving it would make the next submenu open with nothing checked, against the "all selected by default" requirement.
- **Persona count = personas, not files:** a persona may lack one IDE target (`ledger-claude-coordinator` has no VS Code file), so the file count differs per IDE; the number of personas is the one stable figure and equals the `name-mapping.json` entry count.
- **No speculative structure:** the catalog's `agent` warning has a current consumer (three agent-delegating skills after this plan); `getSkillTargetDirs` is consumed by the planner for both scopes; no configurable default (`default_scope` in `_shared.yaml`) is added, because nothing needs to vary it. `PUBLISH_PARTS` has three current entries driving labels, counts, flag parsing and the run plan; `.cli-state.json` is keyed by feature because the CLI already has another repeated prompt (the GUI port in `cmdGui`) that is a natural next remembered value — that trajectory justifies the key, not an extra abstraction; there is no generic state class.

## Pattern Alignment

- **Follows** the thin-script-plus-library pattern (`scripts/lib/name-mapping.js`, `scripts/lib/ctx-generate.js`) for the new `scripts/lib/skill-catalog.js`, `scripts/lib/skill-publish.js` and `scripts/lib/publish-parts.js`.
- **Follows** `scripts/publish-locations.js` as the single place for publish locations.
- **Follows** `parseYamlScalars()` in `scripts/lib/yaml-utils.js` for YAML reading.
- **Follows** the per-stem clear-and-write deploy behaviour of `scripts/publish-skills.js`.
- **Follows** the `--check` convention of `scripts/build-personas.js` and `scripts/cli.js ctx-generate` (read-only, exit 1 when stale).
- **Follows** the generated-artefact classification in `docs/agents/project-manifest/generated-artefacts.md`, adding new rows.
- **Follows** the frozen-registry pattern of `scripts/lib/launch-toggles.js` (`LAUNCH_TOGGLES`) for `PUBLISH_PARTS`.
- **Follows** the pure-reducer-plus-I/O-shell shape of `scripts/lib/launch-agent-core.js` (`reducePickerInput`, `renderPickerLines`, `runInteractivePicker`) for the library's `reduceCheckboxInput` / `buildCheckboxLines` / `runCheckboxPrompt`.
- **Follows** the per-checkout gitignored repo-root state file precedent (`.orchestrator-run.json`) for `.cli-state.json`.
- **Follows** `cli-menu`'s own invariants: zero dependencies, no `process.exit()`, barrel-only `index.ts`, engine-layer placement, mandatory SIGINT cleanup.
- **Departs** from the one-to-one mapping between a CLI command and the script it is named after (`sync-personas` → `scripts/sync-personas.js`): the `sync-personas` command now runs the skills scripts too. Justified by the user's decision to keep the name and hotkey people already use; the script keeps the personas-only meaning, and the help text, menu guide and `development.md` state the difference.
- **Departs** from the previous treatment of `.github/skills/` as a mix of hand-written and copied files: everything under the local skill roots becomes generated output. Justified because a single rule ("edit `skills/`, never `.github/skills/` or `.claude/skills/`") is the only one an agent can follow reliably, and the root AGENTS.md already forbids editing generated output.
- **Departs** from the persona build's convention of ignoring generated output (`personas/*/claude-code/*.md`). Justified above (Rationale → Tracked over ignored); the departure is recorded in `generated-artefacts.md`.
- **Departs** from "CLI menu choices are never persisted" (stated for the agent picker's toggles in `scripts/lib/launch-toggles.js`): the publish selection is the first remembered CLI choice. Justified because the user asked for it explicitly; the departure is limited to interactive use, and agent runs never read it.

- `cli-menu` invariants: zero production dependencies, no `process.exit()`, `src/index.ts` stays a pure barrel, SIGINT cleanup in every raw-mode module.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **A stale global copy shadows the local skill in Claude Code** (personal skills take precedence over project skills) | Publish prints a shadowing warning naming the path; Human Action 1 removes the known copy. |
| **Publish deletes a hand-written directory under `.github/skills/` or `.claude/skills/`** | Orphan removal requires the generated marker; a same-slug overwrite only replaces `SKILL.md` contents that are tracked in git and visible in the diff; tests cover the marker-less case. |
| **Tracked output drifts from its sources** | Build & Maintain regenerates it, CI runs `publish-skills --check`, and the generated-artefacts row gives the discard verdicts. |
| **Feature-branch generator drift in `.github/skills/` gets committed** | The new generated-artefacts row follows the Standing Decision; the Git Committer classifies by that table. A `sync-personas` run on a feature branch now regenerates the local skill output too; the same row covers it. |
| **The marker does not land after the frontmatter because of how the library joins frontmatter and content** | Step 5 verifies on built output; the fallback injects it in the planner; AC-05 tests the deployed file. |
| **`insights-pr-review` is not available in other repositories until it is published globally** (it has never been published to the home directories on this machine, and Build & Maintain publishes local scope only) | Human Action 2 runs the global publish after the run; `skills/README.md` states that global skills need `publish-skills` (or `--scope global`, or the publish action's Skills - Global row). |
| **A caller of `sync-personas` that means "personas only" now publishes skills too** (the default changed) | Step 11 and Documentation Updates switch every known personas-only caller to `--parts personas` (AC-26), and step 20's search finds any left; an interactive caller sees the submenu before anything runs; the root changelog bullet names `--parts personas` as the former behaviour. |
| **`--target vscode` is expected to limit the whole run** | Help text and menu guide state that `--target` / `--custom-path` apply to the personas part only and show `--parts personas --target vscode`; skills always deploy to both IDEs, which is today's `publish-skills` behaviour. |
| **Users keep typing `/changelog` after the rename** | The prompt files are deleted, so the old command no longer exists; `docs/references/development.md` and `skills/README.md` name the new `/insights-changelog` and `/insights-changelog-archive` commands, and the root changelog bullet records the change. |
| **VS Code delegation to the Changelog Curator depends on the active agent's sub-agent tool** | The block tells the agent to perform the task itself when it already is the Changelog Curator; users can also pick the Curator agent before invoking the skill. Documented in `skills/README.md`. |
| **Tests touch real home or repository skill directories** | All routing tests inject temporary roots; the subprocess tests only use `--dry-run` and `--check`. |
| **The CLI fails to start on a machine with the published `cli-menu` 1.1.0** (a missing named ESM export fails at module link time, taking every menu command down) | Human Actions 4–5 order the library release and the constraint bump before the change reaches `main` or another machine; the new cross-system dependency row documents the coupling. |
| **The symlinked library's `dist/` is stale** (the link resolves `cli-menu/dist`, which only `npm run build` refreshes) | Step 1 builds before linking and again after step 2; step 20 runs `node scripts/cli.js help` through the link. |
| **The `cli-menu` refactor changes the setup wizard's checkbox** | `runCheckboxMenu` keeps its signature and becomes an adapter; its existing test file runs unchanged (AC-18). |
| **An agent's `node scripts/cli.js sync-personas` writes into the home skill directories and the repository's skill folders as well as the live agent folders** | Accepted by the user (Resolved Questions 4–5): non-TTY without `--parts` publishes everything, and the help text, menu guide and `live-workspace.md` state it; agents select parts explicitly with `--parts` and preview with `--dry-run`. |
| **A remembered selection silently skips a part the user expects** | The submenu always shows the rows with their checkmarks before anything runs; non-interactive runs never read the stored selection. |
| **Old muscle memory: `p` used to publish personas immediately** | The submenu opens with the last selection pre-checked, so Enter reproduces the previous run; the menu guide and root changelog record the change. |
