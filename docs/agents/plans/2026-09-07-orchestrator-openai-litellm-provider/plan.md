## Summary

Yes — this is implementable, and the Orchestrator is the right (and only necessary) place to add it. LiteLLM exposes an OpenAI-compatible Chat Completions API, and LangChain's `init_chat_model("openai:<model>")` (used internally by `deepagents.create_deep_agent()`, already the orchestrator's model-construction path) resolves its API key and base URL from the standard `OPENAI_API_KEY` / `OPENAI_API_BASE` environment variables with zero custom code. Today, however, the two existing providers (Anthropic, Google) are **not** well separated — both are handled by hand-maintained `if`/`elif` prefix checks duplicated across two functions in `orchestrator/src/config.py`, so adding a provider means editing branch logic in two places that must stay in sync, with nothing stopping them from drifting apart. This plan replaces that shape with a small plug-in registry: a single frozen `LLMProvider` dataclass (`orchestrator/src/utils/llm_providers.py`) whose fields (`name`, `credential_env_var`, `prefixes`, `extra_env_var`, `extra_env_risk`, `register_hook`) capture each provider's model-slug matching, required environment variables, and any one-time setup, with `PROVIDERS` a tuple of three `LLMProvider(...)` instances (Anthropic, Google, OpenAI-compatible). Adding a fourth provider in the future means adding one more `LLMProvider(...)` instance to `PROVIDERS` — no new class and no other function changes. The same idea is mirrored on the root-level pre-flight tooling side (`scripts/preflight-orchestrator.js`), using a `PROVIDER_CHECKS` descriptor array that follows the exact same pattern already established by `scripts/lib/health-checks.js`'s `HEALTH_CHECKS` registry — no new JS pattern is introduced, only a new array entry.

## Architectural Context

The orchestrator resolves one LLM model per pipeline stage via a strict, single-source-of-truth chain: `Config.stage_models` (`orchestrator/src/config.py`) is populated once at startup by `extract_persona_model_slugs()` from persona YAML metadata (`personas/ledger/src/meta/`), optionally overridden by the model-registry assignment system (`personas/model-registry/`). Each stage node (`orchestrator/src/nodes/__init__.py`, `create_stage_node()`) calls `Config.resolve_model_for_stage(stage)` and passes the resulting string straight into `deepagents.create_deep_agent(model=resolved_model, ...)` — never constructing a `BaseChatModel` instance directly. `deepagents` in turn forwards that string, unmodified, to `langchain.chat_models.init_chat_model()`, which is where the actual provider (Anthropic, Google, or now OpenAI-compatible) is selected, purely from the string's shape.

Provider *availability* is currently gated by `_validate_model_api_keys()` inside `load_config()`, a fail-fast check that inspects every configured stage's model slug and raises a single, descriptive `OSError` naming exactly which environment variable is missing for which stage — before any network call is attempted. This is the sole existing extension point for a new provider's validation logic, and constraint #19 in the orchestrator's manifest ("Model Selection Is Persona-Driven — No MODEL_NAME") establishes that provider/model selection must never involve a new environment variable that picks the *model* (only variables that supply *credentials* for an already-selected model are acceptable) — the design below is scoped accordingly.

## Approach / Architecture

1. **Model-slug convention:** adopt LangChain's native `provider:model` string syntax for the new provider — model slugs are written as `openai:<model-name>` (e.g. `openai:gpt-4.1`, or any alias the company's LiteLLM proxy exposes). This requires no new parsing code anywhere in the orchestrator: `init_chat_model` already understands this exact syntax, and `create_deep_agent`'s existing bare-string pass-through already forwards it unchanged.
2. **Routing:** point `langchain-openai`'s `ChatOpenAI` at the company's LiteLLM proxy purely through two environment variables, `OPENAI_API_KEY` (the LiteLLM virtual/master key) and `OPENAI_API_BASE` (the proxy's base URL, including the `/v1` path segment) — both read automatically by `ChatOpenAI`'s environment-validation step. No `ChatOpenAI` instance is constructed anywhere in orchestrator code; the string-based path already does the right thing once these two env vars are set.
3. **Provider plug-in registry (replaces the old ad hoc branches):** introduce `orchestrator/src/utils/llm_providers.py` — a single frozen `@dataclass(frozen=True, slots=True) class LLMProvider` holding `name`, `credential_env_var`, `prefixes: tuple[str, ...]`, `extra_env_var: str | None`, `extra_env_risk: str | None`, and `register_hook: Callable[[], None] | None`, with `matches(model_slug)`, `is_configured()`, `missing_extra_env_vars()`, and `register()` implemented once against those fields, plus a `PROVIDERS: tuple[LLMProvider, ...]` registry of three instances (Anthropic, Google, OpenAI-compatible). Each provider instance owns *all* of its own concerns as data: which model-slug prefixes it matches, which env var is its credential, any extra required env var (only the OpenAI-compatible entry has one — `OPENAI_API_BASE`), and any one-time setup it needs (via `register_hook`). `_validate_model_api_keys()` is reworked, and `_register_provider_profiles()` (item 4 below) is newly added, as generic loops over `PROVIDERS`, with zero provider-specific code left in `config.py` itself.
4. **Responses-API override, expressed as a registered hook:** a standalone module-level function, `_register_openai_profile()`, calls `deepagents.register_provider_profile("openai", ProviderProfile(init_kwargs={"use_responses_api": False}))` — overriding `deepagents`'s own built-in default (`use_responses_api=True` for every `openai:*` spec, intended for native OpenAI), which would otherwise send Responses-API-shaped requests through a LiteLLM proxy that most commonly implements only Chat Completions. It is wired in only via the OpenAI-compatible `LLMProvider` instance's `register_hook=_register_openai_profile` field; the Anthropic and Google instances leave `register_hook=None`, which `LLMProvider.register()` treats as a no-op. `_register_provider_profiles(stage_models)` calls `provider.register()` for each `PROVIDERS` entry whose `matches()` hits at least one configured stage — adding a future provider with its own setup need means writing one new module-level function and pointing `register_hook` at it, nothing else.
5. **Validation, expressed generically over the registry:** `_validate_model_api_keys()` becomes: (a) a top-level guard — `OSError` when `not any(p.is_configured() for p in PROVIDERS)`; (b) a per-stage loop matching each configured model slug to its `LLMProvider` via `matches()`, collecting `provider.credential_env_var` into a `missing` list when `not provider.is_configured()`; (c) a second, distinctly-worded `OSError` for any `provider.missing_extra_env_vars()` entries (currently only the OpenAI-compatible `PROVIDERS` entry's `OPENAI_API_BASE` check) — kept separate from (b) because a missing base URL is a *silent-misrouting* risk, not a *cannot-authenticate* one, and deserves different wording. An unrecognized model-slug prefix (matching no registered provider) is silently skipped, preserving today's existing permissive behavior for out-of-scope slug shapes (e.g. IDE-only display slugs accidentally reused as a model_slug).
6. **Dependency manifest:** add a third optional-dependency extra, `openai = ["langchain-openai>=1.0"]`, mirroring the existing `anthropic`/`google` extras exactly.
7. **Root-level pre-flight tooling, mirroring the same registry idea:** extract `scripts/preflight-orchestrator.js`'s check-function family into a new `scripts/lib/preflight-checks.js` module (mirroring the established `scripts/lib/store-commands.js` extraction pattern) exporting a `PROVIDER_CHECKS` descriptor array — `{ name, envVar, baseUrlEnvVar?, check }` per provider — which is the exact same "array of independently pluggable descriptor objects" idiom already established by `scripts/lib/health-checks.js`'s `HEALTH_CHECKS`. `checkEnv()` and `main()`'s `--check-api-key` block iterate `PROVIDER_CHECKS` generically instead of hardcoded per-provider `if` statements, so a fourth provider needs one new descriptor + one new check function, touching neither `checkEnv()` nor `main()`.

## Rationale

The design deliberately does **zero** custom `ChatOpenAI` construction and **zero** custom string-parsing: every mechanism used (the `provider:model` string syntax, environment-variable-driven `base_url`/`api_key` resolution, and the `ProviderProfile` override hook) is a first-class, documented extension point already shipped by `deepagents`/`langchain`, verified live against the exact versions installed in this workspace (`deepagents==0.6.12`, `langchain==1.3.13`, `langchain-openai==1.6.0` when installed). This keeps the orchestrator's own runtime logic small while still closing the one real, non-obvious gap: without the `ProviderProfile` override, every `openai:`-prefixed call would silently attempt the Responses API against a proxy that likely doesn't support it, producing a confusing runtime failure with no orchestrator-side signal pointing at the cause. Making `OPENAI_API_BASE` a hard requirement (rather than silently falling back to public OpenAI) is the second load-bearing decision — a forgotten env var must not result in the LiteLLM virtual key being sent to `api.openai.com`, which would both fail authentication and defeat the stated purpose of routing through the company hub.

The `LLMProvider` registry exists because the two-providers-today shape was already showing the exact failure mode this workspace's own knowledge base flags ("unvalidated mirrored configuration parameters produce silent data loss" — see Prior Project Context): `_validate_model_api_keys()`'s prefix checks and a would-be `_register_provider_profiles()`'s prefix checks are the *same* classification decision ("which provider does this model slug belong to?") duplicated in two functions, with nothing enforcing agreement between them. A single frozen dataclass plus three data instances is not over-engineering for three providers with a stated intent to add more — it is the minimum shape that lets each provider's matching rule, credential requirement, and setup hook live and be tested in exactly one place, without introducing a new class per provider. The Anthropic and Google instances need only supply a `prefixes` tuple, leaving `extra_env_var`/`extra_env_risk`/`register_hook` at their `None` defaults — the instances are not boilerplate-heavy, they are almost entirely default field values with one populated field each (`prefixes`).

## Pattern Alignment

- **Follows** the existing "one file per cross-cutting concern under `src/utils/`" convention (`persona_models.py`, `store_resolution.py`, `tool_wrappers.py`, etc.) for the new `llm_providers.py`.
- **Follows** the existing `@dataclass(frozen=True, slots=True)` idiom already established in this exact `orchestrator/src/utils/` package — `_InjectCtx`/`_GuardCtx`/`_LogCtx` (`orchestrator/src/utils/tool_wrappers.py`) are three frozen, slotted dataclasses each encapsulating per-case state — `LLMProvider` is the same idiom applied to per-provider state, and is the **first dataclass-based plug-in registry pattern** in this package, not a new inheritance idiom: the orchestrator has zero prior in-house `abc.ABC`/subclass usage, and `PathNormalizationMiddleware(AgentMiddleware)` (`orchestrator/src/utils/path_middleware.py`) subclasses a *third-party* base class, not an in-house one, so it is not itself precedent for introducing one here.
- **Follows** the established lazy, function-local import convention for optional/heavy dependencies (`from src.utils.persona_models import extract_persona_model_slugs` inside `load_config()`; `from deepagents import create_deep_agent` inside `node_fn`) for both the new `from src.utils.llm_providers import PROVIDERS` import and `_register_openai_profile()`'s internal `from deepagents import ProviderProfile, register_provider_profile`.
- **Follows**, on the JS side, the exact "array of independently pluggable descriptor objects" idiom already established by `scripts/lib/health-checks.js`'s `HEALTH_CHECKS: Array<HealthCheck>` (cited in the root `AGENTS.md`) for the new `PROVIDER_CHECKS` array — no new JS pattern introduced, and the `scripts/lib/*.js` pure-module-plus-thin-CLI-wrapper split mirrors `store-commands.js` + `cli.js` for the `preflight-checks.js` extraction.
- **Follows** the append-only, sequentially-numbered constraint convention in `constraints.md` (new constraints **#29**–**#30** appended under a new section, never renumbering #1–28), and the `decisions.md` **Decision** / **Why** / code-comparison format for the new "Adopted" entry.
- **Departs, deliberately, from** the two-providers-today shape of hand-maintained `if`/`elif` prefix chains split across two functions — justified at length in Considered Alternatives and Structural Improvements, and directly requested by way of an explicit architecture question during plan review.

## Detailed Steps

1. **`orchestrator/pyproject.toml`** — add a third optional-dependency extra: `openai = ["langchain-openai>=1.0"]`, placed after the existing `google` extra and before `dev`.
2. **`orchestrator/requirements.txt`** — add a matching `# Optional: OpenAI-compatible provider (e.g. LiteLLM proxy)` comment block with `# langchain-openai>=1.0`, in the same style as the existing Anthropic/Google blocks.
3. **`orchestrator/src/utils/llm_providers.py`** (new file) — define:
   - `_register_openai_profile() -> None` — a standalone module-level function that locally imports `from deepagents import ProviderProfile, register_provider_profile` and calls `register_provider_profile("openai", ProviderProfile(init_kwargs={"use_responses_api": False}))`, with a docstring explaining why (most OpenAI-compatible proxies, including LiteLLM, implement Chat Completions, not the Responses API).
   - `LLMProvider` — a `@dataclass(frozen=True, slots=True)` with fields: `name: str`; `credential_env_var: str`; `prefixes: tuple[str, ...]`; `extra_env_var: str | None = None`; `extra_env_risk: str | None = None`; `register_hook: Callable[[], None] | None = None`. Methods, each implemented once against these fields: `matches(self, model_slug: str) -> bool` (returns `model_slug.lower().startswith(self.prefixes)`, using `str.startswith`'s tuple-argument form); `is_configured(self) -> bool` (returns `bool(os.environ.get(self.credential_env_var, "").strip())`); `missing_extra_env_vars(self) -> list[tuple[str, str]]` (returns `[]` when `self.extra_env_var` is `None` or set; otherwise a single `(self.extra_env_var, self.extra_env_risk)` pair when that env var is unset); `register(self) -> None` (calls `self.register_hook()` when it is not `None`, otherwise a no-op).
   - `PROVIDERS: tuple[LLMProvider, ...]` — the registry, containing three instances:
     - `LLMProvider(name="Anthropic", credential_env_var="ANTHROPIC_API_KEY", prefixes=("claude",))`
     - `LLMProvider(name="Google AI Studio", credential_env_var="GOOGLE_API_KEY", prefixes=("gemini", "models/gemini"))`
     - `LLMProvider(name="OpenAI-compatible", credential_env_var="OPENAI_API_KEY", prefixes=("openai:",), extra_env_var="OPENAI_API_BASE", extra_env_risk=<risk explanation string>, register_hook=_register_openai_profile)`
   - A module docstring states explicitly: "Adding a new provider means adding one new `LLMProvider(...)` instance to `PROVIDERS` — no new class and no other function in this module or in `config.py` needs to change."
4. **`orchestrator/src/config.py`** — rewrite `_validate_model_api_keys(stage_models)` to loop over the registry (`from src.utils.llm_providers import PROVIDERS`, imported locally inside the function): (a) raise the existing "no provider key at all" `OSError` when `not any(p.is_configured() for p in PROVIDERS)`, with its message built from `", ".join(p.credential_env_var for p in PROVIDERS)` so it lists all three (or more, in the future) automatically; (b) loop `stage_models.items()` (de-duplicating by slug as today), find the matching provider via `next((p for p in PROVIDERS if p.matches(model_slug)), None)`, skip silently when no provider matches (preserving today's permissive behavior for unrecognized slug shapes); when matched and `not provider.is_configured()`, append `f"{provider.credential_env_var} (stage {stage!r}, model {model_slug!r})"` to `missing`; also collect `provider.missing_extra_env_vars()` results into a second `extra_missing` list, formatted with the provider's risk explanation; (c) raise the existing-shape `OSError` if `missing` is non-empty; (d) raise a second, distinctly-worded `OSError` if `extra_missing` is non-empty.
5. **`orchestrator/src/config.py`** — define the new `_register_provider_profiles(stage_models: dict[str, str]) -> None` to loop generically: `from src.utils.llm_providers import PROVIDERS` (local import), then for each `provider in PROVIDERS`, call `provider.register()` when `any(provider.matches(slug) for slug in stage_models.values())`. Only the OpenAI-compatible `PROVIDERS` entry's `register_hook` does anything today; the Anthropic and Google entries leave `register_hook=None`, so `register()` is a no-op for them, harmless for Anthropic/Google-only deployments.
6. **`orchestrator/src/config.py`** — in `load_config()`, call `_register_provider_profiles(stage_models)` immediately after the existing `_validate_model_api_keys(stage_models)` call (unchanged call site from the original design).
7. **`orchestrator/.env.example`** — add an `# OpenAI-compatible / LiteLLM proxy (pip install -e ".[openai]")` block with commented `# OPENAI_API_KEY=sk-...` and `# OPENAI_API_BASE=https://litellm.example.internal/v1` lines, placed after the existing Google block.

## Assumptions

- The company's LiteLLM proxy deployment exposes an OpenAI-compatible `/v1/chat/completions` (and `/v1/models`) surface, not the newer `/v1/responses` surface — this is the default and by far the most common LiteLLM proxy configuration, and is exactly why `_register_openai_profile()`'s override (step 3) is necessary.
- Users will configure `OPENAI_API_BASE` to include the `/v1` path segment (matching the OpenAI SDK's own convention), consistent with how `ChatOpenAI` appends endpoint paths directly onto the configured base without inserting `/v1` itself.
- The LiteLLM proxy's model aliases (whatever the company names them on the proxy side) are used verbatim as the `<model-name>` portion of the `openai:<model-name>` slug — no orchestrator-side name translation is introduced.

## Constraints

- Per constraint #19 (`orchestrator/docs/agents/project-manifest/constraints.md`), no new environment variable may select *which model* a stage uses — `OPENAI_API_KEY`/`OPENAI_API_BASE` supply *credentials/routing* for an already-persona-selected model slug, never the slug itself, preserving that constraint.
- The `ProviderProfile` override must be additive (merge on top of `deepagents`'s built-in profile via `register_provider_profile`'s documented merge semantics), never a raw dict replacement that could silently drop other built-in `"openai"` profile keys added by a future `deepagents` release.

## Out of Scope

- Adding first-class `personas/model-registry/default.json` entries (and the corresponding `cc_model` mapping for Claude Code) for OpenAI/LiteLLM models — a separate, personas-subsystem follow-on task; the persona YAML `model_slug:` field already supports assigning an `openai:<model>` slug today with zero further orchestrator changes.
- Any change to `scripts/cli.js` — confirmed already fully generic for `--provider openai`.
- Any change to the MCP server, GUI model-registry API (`mcp-server/gui/api-models.ts`), or root-level `AGENTS.md`/`README.md` — none of these hardcode a provider list.
- LiteLLM proxy-side configuration (model routing, virtual keys, rate limits) — entirely outside this repository.
- Support for the OpenAI Responses API itself (e.g. as an option for a genuinely native-OpenAI deployment) — this plan standardizes on Chat Completions for the `"openai"` provider key workspace-wide, matching the stated migration to a single company hub; a future plan could reintroduce Responses-API support via a per-model `ProviderProfile` override (`register_provider_profile("openai:<model>", ...)`) if ever needed.

## Testing Strategy

Unit tests dominate: every new behavior (provider matching/validation logic, provider-profile registration, the extracted pre-flight check functions) is pure, deterministic logic that can be tested via `unittest.mock.patch.dict(os.environ, ...)` (Python side) and `vi.stubGlobal('fetch', ...)` (Node side) without any real network call or LLM API key. The new `LLMProvider` registry is tested at two levels: `test_llm_providers.py` unit-tests each `PROVIDERS` entry in isolation (matching, env-var checks, `register()` behavior), while `test_config.py::TestApiKeyValidation`/`TestProviderProfileRegistration` retain their existing integration-style role of exercising `load_config()` end-to-end — now backed by the registry rather than inline branches, but asserting the same observable behavior. The one exception, `TestOpenAIEnvVarResolution` (AC-07), intentionally constructs a real `ChatOpenAI` instance (no network call — object construction only) to guard against upstream `langchain-openai` silently changing its environment-variable convention, since that specific fact is load-bearing for the whole feature and not otherwise exercised by any mocked test. Live, real-network tests (`@pytest.mark.live`, `--check-api-key`) are extended for parity with the existing two providers but are not run in CI by default, consistent with existing project convention.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **`langchain-openai` renames its `OPENAI_API_BASE` env-var convention in a future release** (verified today via source inspection of the installed `1.6.0`; not guaranteed stable across major versions) | `TestOpenAIEnvVarResolution` (AC-07) constructs a real `ChatOpenAI` instance and asserts the resolved `openai_api_base` matches the injected env var — this test fails loudly on the next `langchain-openai` upgrade if the convention changes, rather than surfacing as a silent misroute discovered only in production. |
| **A user forgets `OPENAI_API_BASE` and requests silently reach the public OpenAI API instead of the company hub** | The OpenAI-compatible `PROVIDERS` entry's `missing_extra_env_vars()` (step 4's dedicated, hard-fail `OSError`, AC-05) makes this impossible to reach at runtime — `load_config()` refuses to start. |
| **LiteLLM proxy deployment that *does* support the Responses API is later introduced, and the blanket override becomes wrong for it** | The override is scoped to the `"openai"` provider key, not a specific model; a future plan can layer a per-model exception via `register_provider_profile("openai:<model>", ProviderProfile(init_kwargs={"use_responses_api": True}))`, which merges with (and overrides) the provider-level default per `deepagents`'s documented per-key merge semantics — no rework of this plan's mechanism needed, only an additive registration, and no change to the OpenAI-compatible `PROVIDERS` entry itself. |
| **`scripts/lib/preflight-checks.js` extraction inadvertently changes CLI-visible behavior** (e.g. exit codes, message wording) for the four pre-existing functions | Extraction is a mechanical move-plus-parameterize (explicit `envFilePath` argument replacing the module-level `ENV_FILE` constant); Test Plan's `preflight-checks.test.js` covers the pre-existing Anthropic/Google scenarios as well as the new OpenAI ones, so any behavioral drift during extraction is caught before merge. |
| **The `LLMProvider` registry is introduced for three providers and could be seen as premature abstraction** | Each `PROVIDERS` entry populates at most three fields beyond the defaults (`prefixes`, and only the OpenAI-compatible entry also sets `extra_env_var`/`extra_env_risk`/`register_hook`); the dataclass supplies every other behavior via its four methods, so the marginal cost per provider is a handful of field values, not a new class. The design was adopted specifically because the two-providers-today shape had already begun duplicating the same classification decision across two functions — the abstraction pays for itself at three providers, and a Plan Architect Review (Decision 1) confirmed the frozen-dataclass shape as the cheapest correct form, matching this package's own existing `tool_wrappers.py` precedent rather than introducing a class hierarchy. |

## Recommended Workflow
- **Workflow:** standalone
- **Rationale:** All changes are confined to a single, well-understood cross-cutting concern (LLM provider configuration, now expressed as a small plug-in registry) within two closely related codebases already fully mapped by this research (orchestrator + root pre-flight tooling); there is no cross-module dependency ordering beyond what's listed above, and a single developer session with self-review is sufficient — the ledger workflow's formal QA/security-audit/review stages would add process overhead disproportionate to the change's actual risk surface (env-var validation, a documented library extension hook, a small dataclass-based registry, and doc updates).
