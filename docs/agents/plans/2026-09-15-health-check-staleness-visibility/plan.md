## Summary

The workspace's `slow`-tier health checks (`personas-fresh`, `global-cli-linked`) only run inside `doctor`, so a regression in either area is invisible on the everyday menu status line between `doctor` runs — a user can trust a green status that is actually stale. This plan adds two independent, additive pieces: (A) a hash-based `fast`-tier promotion for the self-contained `personas-fresh` check, letting its source-drift signal appear on every menu open without a subprocess spawn — wired into the existing instant-tier status line via a small, explicit filter extension (see Detailed Steps) — while keeping the existing spawn-based full diff as `doctor`'s deeper ground truth; and (B) a staleness-nudge second status line that persists the outcome of every `doctor` run and surfaces, on every subsequent menu open, how long ago the last full check ran and whether any `slow`-tier check failed then and hasn't been re-verified since. `global-cli-linked` (and the existing `fast`-tier `global-mcp-registered`, which only checks config-file existence, not real IDE-registration validity) explicitly stay spawn/existence-check-based and `doctor`-only — externally-mutable state cannot be safely cached without reintroducing the exact false-confidence problem this plan solves.

## Architectural Context

`scripts/lib/health-checks.js` is the single source of health-check detection logic, exporting `HEALTH_CHECKS` (a flat array of `{id, label, cost, detect(), fix?}` entries across three cost tiers — `instant`, `fast`, `slow`) and `runChecks(costFilter)`. `scripts/cli.js` consumes this registry two ways: `STATUS_LINES` (currently one `() => string` renderer, run synchronously on every menu open, filtering to `instant`-tier checks only) and `cmdDoctor()` (`await runChecks('all')`, printing every tier's result and exiting non-zero on any failure). The persona build pipeline (`scripts/build-personas.js`) is a thin `!CHECK`-gated wrapper around `@mistralys/persona-builder`'s CLI, with two existing post-build side-effect steps (`personas/package.json` version sync, `personas/name-mapping.json` regeneration) that only run on a real build, never on `--check`/`--dry-run`. The workspace has exactly one existing user-level (not per-checkout) persistent-state directory, `~/.ai-insights/`, established by `scripts/install-mcp-global.js` for the MCP shim's `config.json` and reused by `health-checks.js`'s `global-mcp-registered` check.

## Approach / Architecture

**Piece A — hash-based fast-tier promotion for `personas-fresh`:**

1. New module `scripts/lib/persona-hash-cache.js` exports `computeSourceHash(inputPaths)` (a deterministic SHA-256 over every file's `relativePath\0content` pair across the given paths, sorted for OS-independent ordering), `readHashCache(cachePath)` / `writeHashCache(cachePath, hash)` (JSON `{ hash, generatedAt }`, fail-safe: any read/parse error returns `null`), `isPersonaSourceFresh({ cachePath, inputPaths } = {})` (the synchronous boolean used directly as a `detect()` function — `false` whenever the cache is missing, corrupt, or its hash disagrees with a freshly recomputed one), `writePersonaHashCache({ inputPaths, cachePath } = {})` (resolves the same defaults as `isPersonaSourceFresh`, computes `computeSourceHash(inputPaths)`, and calls `writeHashCache(cachePath, hash)` — the single function `build-personas.js`'s post-build step delegates to, kept directly callable so it can be unit-tested against a fixture directory instead of only through a live build; see Test Plan), and `clearFreshnessMemo()` (test-only reset hook, see below). Default `inputPaths` are read from `personas/persona-build.config.js` via the same `createRequire()` ESM/CJS bridge `build-personas.js` already uses (L20), rather than hardcoding a second copy of the suite path list: the three suites' `srcDir`s, `sharedPartialsDir`, plus `persona-build.config.js` itself, the `personas/plugins/` directory, and `personas/model-registry/` (none of the last three live under a suite `srcDir`, yet all affect build output — `personas/model-registry/` is read at module scope by the ledger plugin and its resolved `cc_model`/`model` values are rendered into every persona's frontmatter across all three suites, so a model reassignment must also invalidate the cache; `personas/plugins/` and `personas/model-registry/` are both constructed directly as sibling paths of `personas/`, the same way the ledger plugin itself resolves `MODEL_REGISTRY_DIR`, since neither is exported by `persona-build.config.js`). `isPersonaSourceFresh()` memoizes its boolean result in a module-level `Map` keyed by the resolved `cachePath` plus serialized `inputPaths`, performing the walk-and-hash at most once per process for a given key and returning the memoized value on every subsequent call — this matters because `@mistralys/cli-menu`'s interactive menu loop re-invokes every `STATUS_LINES` renderer (and therefore this `detect()`) after every command, not once per session, so an unmemoized implementation would re-walk and re-hash the full persona source tree on every return to the menu. `clearFreshnessMemo()` clears this in-process cache and exists solely so tests can observe a fresh-to-stale transition within a single test file without spawning a new process.
	The default input set additionally includes `shared/workflow-manifest.json`, because `persona-build.config.js` imports its roles into the ledger plugin. `isPersonaSourceFresh()` recomputes its bounded source hash on every call; no process-lifetime or cache-identity memo may suppress detection of a source edit made while the menu remains open.
2. `scripts/build-personas.js` gains a third `if (!CHECK) { ... }` post-build block (matching the existing two) after the delegated build and name-mapping regeneration. It calls `writePersonaHashCache()` with no arguments inside `try/catch`; a write failure warns and continues, while a failed delegated build never reaches this block. Delegating to an exported function keeps cache correctness unit-testable without spawning the script, and a static wrapper test verifies the import, guard, placement, and error boundary (see Test Plan, AC-04).
3. `scripts/lib/health-checks.js` gains one new `fast`-tier entry, `personas-hash-fresh` (label: "Personas source unchanged since last build"), whose `detect()` is `isPersonaSourceFresh()`. The existing `slow`-tier `personas-fresh` entry (full spawn-based diff via `build-personas.js --check`) is **not** removed or renamed — it remains `doctor`'s deeper ground-truth check, since the hash comparison is a deliberately narrower guarantee (see Rationale).
4. `scripts/cli.js`'s existing instant-tier `STATUS_LINES[0]` renderer's filter is extended from `HEALTH_CHECKS.filter(c => c.cost === 'instant')` to `HEALTH_CHECKS.filter(c => c.cost === 'instant' || c.id === 'personas-hash-fresh')`, so the new check's live `detect()` result is included in the same failures/fix-hint list already rendered on every menu open — this is what actually delivers Piece A's stated visibility goal; without it, the new check would only ever be evaluated during `doctor`, identical to the `slow`-tier check it is meant to improve on. No new rendering logic is introduced: the existing `failures[]` mechanism (already built to iterate an arbitrary filtered subset of `HEALTH_CHECKS`) picks up the new entry unmodified.

**Piece B — staleness-nudge status line:**

5. New module `scripts/lib/doctor-history.js` exports `HISTORY_PATH` (`~/.ai-insights/last-doctor-run.json`, following the existing user-level state-directory precedent), `writeDoctorRun(results, slowCheckIds, historyPath)`, `readDoctorRun(historyPath)`, and `buildStalenessLines(doctorRun, slowCheckIds, now = new Date())`. `writeDoctorRun()` persists `{ schemaVersion: 1, ranAt: <ISO8601>, results: [{id, label, passed}, ...], slowCheckIds }`: it creates the parent directory, writes a uniquely named temporary sibling file, then renames it over the old history so readers see either a complete old record or a complete new one. `readDoctorRun()` treats missing, malformed, or schema-invalid data as `null`. The pure renderer compares the stored slow-check-id snapshot with the current ids before making a full-check recency claim, and stays extractable because `scripts/cli.js` cannot be imported safely by tests.
6. `scripts/cli.js`'s `cmdDoctor()` derives the current `slowCheckIds` from `HEALTH_CHECKS` and calls `writeDoctorRun(results, slowCheckIds)` immediately after `runChecks('all')`, including failed health-check results. The persistence attempt is best-effort: catch an I/O failure, emit a yellow history-unavailable warning, then preserve the existing result logging and exit behavior derived solely from health results.
7. `scripts/cli.js`'s `STATUS_LINES` gains a second thin renderer that passes `readDoctorRun()` and the current slow-check ids to `buildStalenessLines()`. That helper renders a yellow `No trustworthy full-check record` message for absent/corrupt/schema-invalid data; renders the dimmed `Last full check: N day(s) ago` line plus still-registered prior slow-check failures only when the stored and current id sets exactly match; and otherwise warns that the record predates the current full-check set and directs the user to `doctor`, without claiming coverage or carrying forward stale failure status.

Both pieces are purely additive: no existing `detect()` contracts, `HEALTH_CHECKS` entries, or `runChecks()` behavior change. `STATUS_LINES[0]`'s filter predicate is the one direct edit to existing `scripts/cli.js` rendering logic this plan makes, and is scoped to a single explicit `id` addition (step 4).

The detailed doctor-history contract in steps 5–8 supersedes the initial shorthand above: persisted history is versioned and atomically replaced, a history-write failure is advisory only, and recency/failure carry-forward is allowed only when the stored slow-check snapshot exactly equals the current slow tier.

**Cycle-2 precision:** `isPersonaSourceFresh()` owns the full fail-closed boundary required by direct synchronous menu rendering: it must catch errors from reading the cache and from resolving, walking, reading, and hashing every source input, returning `false` rather than allowing an exception to escape. `writePersonaHashCache({ inputPaths, cachePath, writeCache = writeHashCache } = {})` is the exact writer contract: `writeCache` is a test-only dependency-injection option, receives `(resolvedCachePath, hash)`, returns its delegate result, and deliberately propagates a delegate error. `build-personas.js` continues to call it without options and catches that propagated failure at the post-build wrapper boundary, preserving production behavior. Slow-check coverage is set equality, not registry-order equality: `buildStalenessLines()` must compare normalized `Set` membership and cardinality, so identical IDs in a different array order remain covered.

## Rationale

The hash-based check is legitimate to cache because `personas-fresh` is self-contained — only `build-personas.js`, this workspace's own tooling, can regenerate persona output — matching the plan's stated acceptance criterion for when caching is safe. `global-cli-linked` and `global-mcp-registered` are deliberately excluded from any caching scheme because their underlying state is externally mutable (`npm unlink`, an `nvm` switch, a cleared global `node_modules`, IDE config edited by hand); an optimistic "still true" cache for those would keep reporting green after a silent drift, which is strictly worse than today's "simply not shown between `doctor` runs" gap, since it would look like a positive signal instead of an absent one.

The hash check deliberately keeps the existing slow full-diff check alongside it rather than replacing it, because the two provide different guarantees: the hash only detects changes to source *inputs* (suite `srcDir`s, shared partials, the build config, the ledger plugin code, and the model registry), while `build-personas.js --check`'s full template-render diff also catches drift in the *generated output itself* — e.g. a hand-edited `.md` file under `personas/ledger/vs-code/` that no longer matches what the current source would regenerate, with the source hash unchanged. This is a real, narrower guarantee, not a strict subset of the old check's coverage, and is called out explicitly here rather than silently accepted: the fast hash check is a cheap **early signal** surfaced on every menu open; `doctor`'s existing slow full-diff check remains the authoritative verification.

The freshness check intentionally computes the bounded source hash for every status render. `@mistralys/cli-menu` re-renders status lines after every command, and a cache-identity-only memo would report a stale prior result when source files change without a simultaneous cache write. Recomputing eliminates that false-green path while remaining synchronous and subprocess-free; the implementation must measure and keep the bounded traversal within the documented fast-tier budget.

## Pattern Alignment

- Follows the established `scripts/lib/*.js` single-responsibility module shape (alongside `npm-link.js`, `claude-cli.js`, `store-commands.js`) for both new modules — no departure.
- Follows `health-checks.js`'s existing rule that detection logic needing independent testability is a named exported helper, not an inline `detect()` closure (matching `lockfileFresh`) — `isPersonaSourceFresh()` follows this shape.
- Follows `build-personas.js`'s existing `if (!CHECK) { ... }` sequential post-build-step pattern (version sync, name-mapping regeneration) — the new hash-cache write is a third block in the same shape, not a new mechanism.
- Follows `install-mcp-global.js`'s precedent of accepting an override parameter (e.g. `historyPath`/`cachePath` arguments defaulting to the real path) so tests can redirect file I/O into a temp directory — both new modules adopt this seam.
- Follows the same testability-driven extraction principle already applied to `writePersonaHashCache()` (Considered Alternatives: AC-04 positive-half testability) — the Piece B staleness-nudge renderer's message-building logic is extracted into `doctor-history.js`'s exported `buildStalenessLines()` rather than left inline in `scripts/cli.js`'s `STATUS_LINES`, since `scripts/cli.js`'s top-level `process.exit`-calling side effect makes it unsafe to import in a test.
- Departs from nothing in `HEALTH_CHECKS`'s array-literal registry shape — the new entry is added the same way every existing entry was added.
- Deliberately departs from memoizing fast-tier results: `@mistralys/cli-menu` re-renders synchronously after every command, and the required current-source guarantee takes precedence over avoiding a bounded source walk. The hash input graph remains explicitly bounded and gets a timing obligation rather than establishing a cache convention that would hide edits.
- Extends `scripts/cli.js`'s existing `STATUS_LINES[0]` failures-list mechanism (already designed to iterate an arbitrary filtered subset of `HEALTH_CHECKS`) by widening its filter predicate — no new rendering code, matching the existing single-summary-line convention rather than introducing a second exception to it (Piece B's dedicated second line is reserved for genuinely different-shaped content, per Considered Alternatives).

## Assumptions

- Exactly one active checkout of this workspace exists per user machine at a time, matching the existing `~/.ai-insights/config.json` single-`repoPath` precedent — the new `last-doctor-run.json` inherits this same assumption rather than introducing per-checkout namespacing that no other file in this directory has.
- `personas/persona-build.config.js`'s exported `suites` and `sharedPartialsDir` fields remain the authoritative, sole declaration of persona source locations (per existing Structural Observations) — the hash-cache module reads them rather than hardcoding a duplicate path list, so it stays correct if a suite is added/removed/moved in the future.
- `personas/model-registry/` is a fixed, well-known path relative to `personas/` — not exported by `persona-build.config.js` — matching how `personas/plugins/ledger/index.js` itself resolves `MODEL_REGISTRY_DIR` as `path.join(__dirname, '..', '..', 'model-registry')`; the hash-cache module constructs this path directly, the same way it already does for `personas/plugins/`.
- A cache write failure (e.g. a read-only `personas/` directory) during `build-personas.js`'s post-build step should warn and continue, not fail the build — matching the existing precedent at L72–73 for the version-sync step's missing-changelog-entry case.

## Constraints

- Cross-platform: both new modules use only `fs`, `path`, `os`, `crypto` (all cross-platform stdlib), `path.join`/`path.resolve` exclusively for path construction, and no shell-dependent operations — consistent with AGENTS.md's Cross-Platform Policy.
- `scripts/lib/health-checks.js` must not import from `scripts/cli.js` or `SETUP_COMPONENTS` (existing header constraint, L17-18) — `persona-hash-cache.js` must likewise avoid importing from `scripts/cli.js`.
- Cache/history reads must fail safe: any missing file, unreadable file, or JSON parse error must be treated as "not fresh" / "never run" — never as a false positive. This applies to `readHashCache`, `isPersonaSourceFresh`, and `readDoctorRun` alike.
- `isPersonaSourceFresh()` is the error boundary for live source traversal: any error while resolving input paths or walking, reading, or hashing a configured source input must return `false` without throwing into `STATUS_LINES`; a deleted or unreadable hashed input is stale, never a menu-render failure.
- `writePersonaHashCache()` must preserve its exact test seam: `writeCache` defaults to `writeHashCache`, receives `(resolvedCachePath, hash)`, and may throw; only `scripts/build-personas.js` catches that error to warn and continue after a successful delegated build. No production override is added.
- Slow-check coverage equality is order-independent set equality. The renderer must normalize by `Set` membership and cardinality; registry order must not turn an otherwise identical stored/current slow-check collection into a coverage-mismatch warning.
- `personas-hash-fresh`'s `detect()` must remain synchronous and return a plain boolean (no `Promise`), satisfying the existing `fast`-tier contract enforced by `scripts/tests/health-checks.test.js`'s AC-2b and `STATUS_LINES[0]`'s runtime `Promise`-guard.
- `isPersonaSourceFresh()` must compare the cache to a newly computed hash of its exact resolved `cachePath`/`inputPaths` inputs on every call. It may not reuse a prior boolean based only on cache identity, because source files can change while the cache remains untouched.

## Out of Scope

- Any caching or tier change for `global-cli-linked` (stays `slow`, spawn-based, `doctor`-only) or `global-mcp-registered` (stays `fast`, existence-check-based) — both are externally-mutable state where an optimistic cache would actively regress trust, per this plan's Background. `global-mcp-registered`'s known limitation (config-file existence is not proof of real IDE-registration validity) is a pre-existing condition, documented here as a caveat, not addressed by this plan.
- Any change to `build-personas.js --check`'s existing full-diff behavior or exit codes.
- A UI/config toggle to disable the staleness-nudge line — it always renders once history exists, matching every other `STATUS_LINES` entry's unconditional-render convention.
- Retroactively backfilling `last-doctor-run.json` for users who have already run `doctor` before this plan ships — the first post-upgrade `doctor` run naturally establishes the baseline; before that, the status line correctly shows "never run."

## Acceptance Criteria

- AC-01: `HEALTH_CHECKS` contains a new `fast`-tier entry `personas-hash-fresh` whose `detect()` returns `true` immediately after a real `build-personas.js` run (cache freshly written) and `false` when any file under a hashed input path changes afterward, without spawning a subprocess; and `scripts/cli.js`'s `STATUS_LINES[0]` renderer's filter includes this check's `id` alongside `c.cost === 'instant'`, so a `false` result is surfaced (as a warning line with its `fix` hint) on every menu open, not only during `doctor`.
- AC-02: The existing `slow`-tier `personas-fresh` entry (spawn-based full diff) is unchanged in id, label, cost, and behavior.
- AC-03: `isPersonaSourceFresh()` returns `false` (not throw, not `true`) when the cache file is missing, unreadable, or contains malformed JSON, and also when resolving, traversing, reading, or hashing any configured source input fails.
- AC-04: `build-personas.js` (real build, not `--check`/`--dry-run`) writes a hash cache reflecting the current suite `srcDir`s, `sharedPartialsDir`, `persona-build.config.js`, `personas/plugins/`, `personas/model-registry/`, and direct `shared/workflow-manifest.json` input; `--check`/`--dry-run` does not write or modify the cache. `writePersonaHashCache({ inputPaths, cachePath, writeCache = writeHashCache } = {})` calls and returns its supplied writer delegate, propagating a delegate error for the wrapper's existing planned `try/catch` recovery.
- AC-05: Two consecutive same-process calls to `isPersonaSourceFresh()` must detect a change to any hashed source input made between the calls while the cache file is unchanged; a subsequent successful `sync-personas` cache write restores `true` on the next render when inputs then match. Removal or loss of readability of a hashed input between those calls returns `false` without throwing.
- AC-06: `cmdDoctor()` atomically persists `{ schemaVersion, ranAt, results, slowCheckIds }` after every invocation, including failed health checks; a history-write failure produces a warning but never changes the health-results-derived exit behavior.
- AC-07: With absent, corrupt, or schema-invalid history, the status line shows `No trustworthy full-check record`; with an exact order-independent stored/current slow-check-ID set match it shows recency plus still-registered prior failures, but never asserts a current slow-check pass from cached data. The same IDs in a different array order are equal and render this ordinary recency branch.
- AC-08: When the stored slow-check-ID set differs from the current slow tier because a check was added, removed, or reclassified, the status line warns that the record predates the current full-check set and directs the user to `doctor`, without making a recency/coverage claim or carrying forward stale failure status.
- AC-09: All new `detect()`/status-line functions remain cross-platform (no hardcoded path separators, no shell-only utilities) and complete within their documented fast/instant budgets without subprocess spawns.

## Testing Strategy

The preceding high-level description is superseded where it describes AC-04 positive-half coverage as helper-only. AC-04 uses two layers: fixture tests prove `writePersonaHashCache()` persists the current hash, and the established static source-text approach proves `scripts/build-personas.js` imports it and invokes it after the delegated build only inside `if (!CHECK)`, within a `try/catch` that warns and continues. The writer seam is exact and deterministic: fixture tests pass `writeCache: () => { throw new Error('injected write failure'); }` to `writePersonaHashCache()` and assert that it propagates; the static wrapper test verifies that the production `try/catch` is the recovery boundary. This leaves the no-option production call and its real write behavior unchanged. A real build remains excluded because its fixed workspace paths rewrite generated output. Hash-cache tests use fixture `cachePath`/`inputPaths`; doctor-history tests use `historyPath`; and only the AC-04 negative-half `--check` subprocess touches the real checkout after establishing a known cache baseline. The test suite must remove a hashed fixture input after writing its cache and assert `isPersonaSourceFresh()` returns `false` without throwing, and must pass identical slow-check IDs in different orders to `buildStalenessLines()` and assert that ordinary recency/failure rendering remains selected.

Unit tests via Vitest under `scripts/tests/`, matching this workspace's existing convention for `scripts/lib/*.js` modules (no live subprocess spawns in the new tests other than the single AC-04 negative-half `--check` invocation described below; all other file I/O is redirected into a Vitest-managed temp directory via each function's override parameter — `cachePath`/`inputPaths` for the hash-cache module, `historyPath` for the doctor-history module). The existing `scripts/tests/health-checks.test.js` suite is extended, not restructured, to keep the generic tier-shape assertions (AC-2, AC-2b, AC-3, AC-4) automatically covering the new entry. AC-04's positive half (a real build writes the cache) is verified by calling the exported `writePersonaHashCache()` directly against fixture paths rather than by spawning `build-personas.js` itself — `build-personas.js`'s `ROOT`/`PERSONAS` constants have no override seam, and a real (non-`--check`) invocation would mutate the live checkout's generated persona output, so no test in this plan invokes it without `--check`. AC-04's negative half (`--check` never writes or modifies the cache) does not assume the real `personas/.persona-build-cache.json` already exists on a fresh checkout: the test first calls `writePersonaHashCache()` (no arguments, real default paths — not a `build-personas.js` invocation, so this does not violate the previous sentence's constraint) to establish a known baseline deterministically regardless of prior state, captures that baseline's mtime and stored hash, then spawns `--check` and asserts both are unchanged afterward. AC-06/AC-07's staleness-nudge message logic is verified the same way in spirit: `buildStalenessLines()` is a pure function of its arguments with no file I/O of its own, so its tests pass fixture `doctorRun` objects and id arrays directly, without touching `readDoctorRun()`'s real file path or importing `scripts/cli.js` (which cannot be safely imported — see Considered Alternatives: Staleness-nudge message construction). AC-01's menu-open visibility half is verified the same way `scripts/tests/cli-cmd-agent.test.js` already verifies `cmdAgent()`'s cwd fix: a static source-text assertion against `scripts/cli.js`'s raw contents (via `fs.readFileSync`), confirming `STATUS_LINES[0]`'s filter predicate literally includes `c.id === 'personas-hash-fresh'`, since `scripts/cli.js` itself cannot be imported for the reason above.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **The narrower hash-check guarantee is misunderstood as a full replacement for `doctor`'s deep check, and a future contributor later removes the slow check as "redundant."** | Explicitly documented in this plan's Rationale and in the `menu-guide.md` update; the `personas-hash-fresh` check's own label ("source unchanged since last build") is phrased to avoid implying full build-output correctness. |
| **Hashing persona sources on every menu render adds latency.** | The input graph is explicitly bounded to known build inputs, no subprocess is spawned, and the fixture test measures the traversal against the documented fast-tier budget. Correctness takes priority over a cache-identity memo that would hide same-session source edits. |
| **A cache-write failure could turn a successful persona build into a failed command or leave an ambiguous cache state.** | `build-personas.js` invokes the writer only after the delegated build succeeds and catches any writer failure, emits a warning, and preserves the successful build exit path; unit and source-text tests cover the writer seam and wrapper boundary. |
| **A source file disappears or becomes unreadable while the menu is rendering, causing a status-line exception.** | `isPersonaSourceFresh()` catches every cache and source traversal/read/hash error and returns `false`; the fixture test removes a hashed input after cache creation to exercise the deterministic traversal-error path. |
| **`~/.ai-insights/last-doctor-run.json` silently accumulates stale state across unrelated checkouts if a user switches repos without realizing the assumption.** | Documented explicitly in Assumptions and Out of Scope; matches the pre-existing single-checkout assumption already baked into `config.json` in the same directory, so this plan introduces no new class of risk beyond what already exists. |
| **Doctor history is interrupted or the registry evolves after it is saved, causing a recency line to overstate what was checked.** | Atomic replace preserves the prior complete record on interruption; schema validation treats untrustworthy input as absent; a stored slow-check snapshot must exactly match the current set before rendering full-check recency or prior failures. |
| **A harmless `HEALTH_CHECKS` registry reorder is reported as stale doctor coverage.** | `buildStalenessLines()` compares stored and current slow IDs as `Set`s by membership and cardinality; a regression test exercises equal IDs in different orders. |
