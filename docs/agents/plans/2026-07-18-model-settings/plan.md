## Summary

Implement configurable model settings for the persona system, replacing hardcoded YAML-only model configuration with a GUI-managed model registry and per-persona model assignment system. Users will be able to register available models, assign them to individual personas across all three suites (ledger, standalone, ledger-support), and set a default model — all through the existing GUI's Configuration screen, restructured with tabs. Each model registry entry includes a `cc_model` field (the Claude Code model setting, defaulting to `"inherit"`), allowing per-persona Claude Code model configuration alongside the VS Code / orchestrator model. A built-in "Inherit / Auto" model option (slug `inherit`) lets users defer model selection entirely: VS Code omits the `model` frontmatter field (using whatever model the user has selected in the model picker), Claude Code gets `model: 'inherit'` (deferring to the user's configured model), and the orchestrator skips the override (falling back to YAML-based resolution). The model assignments will be consumed by both the persona build system (injecting into generated output for all suites) and the orchestrator (resolving models at runtime), with a clear priority chain: user assignments > per-persona YAML > shared YAML default. A "Rebuild Personas" button in the GUI triggers the persona build directly, closing the configure-then-apply loop without requiring manual CLI invocation.

## Architectural Context

The system currently resolves model slugs through a two-layer YAML mechanism:

1. **Suite-wide default:** `personas/ledger/src/meta/_shared.yaml` → `default_model` / `default_model_slug` (currently `Claude Sonnet 4.6`)
2. **Per-persona override:** Individual YAML files (e.g., `1-planner.yaml`) optionally set `model` / `model_slug` (currently only Planner and PM override to `Claude Opus 4.6`)

The persona build system (`personas/plugins/ledger/index.js`) resolves model values at build time via fallback logic and injects them into templates (VS Code frontmatter gets `model: '{{model}}'`). The orchestrator (`orchestrator/src/utils/persona_models.py`) independently reads the same YAML files at startup to populate `Config.stage_models`.

The GUI runs as an HTTP server from `mcp-server/gui/`, with settings stored at `{ledgerRoot}/gui-config.json`. The server has access to `WORKSPACE_ROOT` (derived from `mcp-server/..` in `mcp-server/src/utils/ledger-root.ts`), which enables it to locate files in the `personas/` directory.

The `name-mapping.json` file is auto-generated by `scripts/build-personas.js` on every build but currently omits model fields from its entries.

## Approach / Architecture

Introduce a file-based model registry and assignment system at `personas/model-registry/` with three files:

- **`default.json`** — shipped default models (tracked in Git)
- **`local.json`** — user-registered models (gitignored, auto-created on first use)
- **`assignments.json`** — per-persona model assignments + default model selection (gitignored, auto-created on first use)

The GUI Configuration screen is restructured with a tab system (General, Persona Models, Model Registry). New API endpoints provide bulk save for the model registry and CRUD for assignments. Both the persona build system (all three suite plugins — ledger, standalone, ledger-support) and the orchestrator are updated to read `assignments.json` as the highest-priority override layer in the model resolution chain:

```
assignments.json (user GUI config) > per-persona YAML > _shared.yaml default
```

The `name-mapping.json` generation is extended to include `model` and `model_slug` fields, reflecting the resolved model for each persona after the full priority chain is applied.

## Rationale

- **Separate files for registry vs. assignments** — different lifecycles: registry is "what's available", assignments is "what's chosen". Both are gitignored (except shipped defaults) because model preferences are per-developer.
- **`default.json` is a seed, not a runtime layer** — shipped defaults are copied into `local.json` on first access (auto-initialization) or via the "Load Defaults" button. Once copied, entries are fully editable and deletable like any user-registered model. There is no concept of "built-in" vs "custom" at runtime — `local.json` is the single source of truth for the model list. `default.json` exists solely so new installations start with a sensible set of models and so future releases can introduce new defaults via "Load Defaults".
- **Files in `personas/model-registry/`** — colocated with the persona source they configure. Both the build system and orchestrator already operate relative to the workspace root and can locate this directory. The GUI accesses it via the existing `WORKSPACE_ROOT` constant.
- **Priority chain preserves YAML as fallback** — users who never touch the GUI get the same behavior as today. The GUI is purely additive.
- **All persona suites supported** — model assignments use persona `id` from `name-mapping.json` (e.g., `ledger-1-planner`, `developer-standalone`, `standalone-ledger-bootstrapper`) as keys, covering all three suites. This ensures every persona in the system can have a model override, not just the 9 ledger personas.
- **UUID values in assignments, resolved at consumption** — `assignments.json` stores model UUIDs as values rather than slugs. UUIDs are stable across slug renames, eliminating the class of sync bugs that arise when slugs are changed out-of-band (bypassing any cascade). Both the build system and orchestrator read `assignments.json` alongside `local.json`, build a UUID-to-slug map, and resolve locally before applying the priority chain. The `getResolvedAssignments()` function in `model-registry.ts` provides the same resolution for API consumers. The frontend works with UUIDs directly and resolves them to model names client-side using the already-loaded model registry.
- **Bulk save, not instant CRUD** — the Model Registry tab and Persona Models tab both use a local-state-then-save pattern: edits accumulate in the frontend, dirty indicators show what changed, and a single Save button commits everything. This avoids partial-state problems (e.g., a failed mid-edit API call leaving the registry inconsistent) and gives users a clear undo path (just don't save).
- **Tab system follows knowledge.js pattern** — the only existing tab implementation in the GUI; reusing the same pattern maintains visual consistency and avoids introducing a new abstraction for a single use.

## Detailed Steps

### 1. Create model registry default file

Create `personas/model-registry/default.json` with the shipped default models. Each entry includes a `cc_model` field for the Claude Code model setting (rendered into Claude Code frontmatter as `model: '{{cc_model}}'`). Anthropic models use `"inherit"` (defer to user's Claude Code config), while non-Anthropic models specify the model name explicitly since Claude Code cannot inherit a non-Anthropic model:

```json
[
  { "id": "00000000-0000-0000-0000-000000000000", "name": "Inherit / Auto", "slug": "inherit", "cc_model": "inherit" },
  { "id": "00000000-0000-0000-0000-000000000001", "name": "Claude Opus 4.6", "slug": "claude-opus-4-6", "cc_model": "inherit" },
  { "id": "00000000-0000-0000-0000-000000000002", "name": "Claude Sonnet 4.6", "slug": "claude-sonnet-4-6", "cc_model": "inherit" },
  { "id": "00000000-0000-0000-0000-000000000003", "name": "Gemini 3.5 Flash", "slug": "gemini-3-5-flash", "cc_model": "gemini-3-5-flash" }
]
```

Default entries use deterministic zero-namespace UUIDs so they are stable across installations and can be referenced reliably by `loadDefaults()` merge logic (match by `id`, not by slug).

The `inherit` entry is a sentinel: when assigned to a persona, the build system omits the `model` field from VS Code frontmatter (so the user's model picker selection is used), sets `model: 'inherit'` in Claude Code frontmatter, and the orchestrator skips the assignment (falling back to YAML-based resolution).

### 3. Create model registry backend module

Create `mcp-server/src/gui/model-registry.ts` — a self-contained module for reading/writing model registry and assignment data:

**Data types (Zod schemas):**
- `ModelEntrySchema`: `{ id: z.string().uuid(), name: z.string().min(1), slug: z.string().regex(/^[a-z0-9]+(-[a-z0-9]+)*$/), cc_model: z.string().min(1).default('inherit') }` — `id` is a stable UUID primary key for save operations, independent of slug/name. `cc_model` is the Claude Code model setting (rendered into CC frontmatter); `"inherit"` defers to the user's Claude Code config, any other value specifies the model explicitly. The slug `"inherit"` is reserved for the built-in "Inherit / Auto" model and must not be used for user-created models
- `ModelRegistrySchema`: `z.array(ModelEntrySchema)`
- `ModelAssignmentsSchema`: `{ default_model_uuid: z.string().uuid().optional(), persona_models: z.record(z.string(), z.string().uuid()) }` — keys in `persona_models` are persona `id` values from `name-mapping.json` (e.g., `ledger-1-planner`, `developer-standalone`, `standalone-ledger-bootstrapper`), covering all three suites. Values are model UUIDs — stable primary keys that remain valid even if a model's slug is renamed. Slug resolution is performed by `getResolvedAssignments()` (for API consumers) or by reading both `assignments.json` and `local.json` and building a UUID-to-slug map locally (for the build system and orchestrator). The `cc_model` value is resolved by looking up the assigned model UUID in the registry — no separate `cc_model` assignment is needed

**Public functions:**
- `getModelRegistryPath()` → returns `join(WORKSPACE_ROOT, 'personas', 'model-registry')`
- `readModels()` → reads `local.json`. If `local.json` does not exist, auto-initializes it by copying `default.json` contents, then returns the result. Returns `ModelEntry[]`
- `writeModels(models: ModelEntry[])` → validates all entries (schema + slug uniqueness + reserved slug `"inherit"` only allowed for the built-in sentinel UUID), detects deletions of referenced models by UUID (calls `isModelReferenced(entry.id)` for each removed entry — if any are referenced, returns `{ saved: false, referencedModels: [...] }` with the list of usages so the caller can surface them to the user), then atomic-writes the updated model array to `local.json`. No slug-change cascade is needed — assignment values are model UUIDs, which are stable regardless of slug renames. Returns `{ saved: true, models: ModelEntry[] }` on success
- `readAssignments()` → reads `assignments.json` (returns default structure if file doesn't exist), returns `ModelAssignments`
- `writeAssignments(data: ModelAssignments)` → validates + atomic write to `assignments.json`
- `loadDefaults()` → reads `default.json`, merges into `local.json` (add entries with missing IDs, keep existing entries). When a default entry has the same `id` as an existing local entry, the local entry wins (no overwrite). When a default entry has a different `id` but the same `slug` as an existing local entry, this is a **conflict** — the entry is not added, and the conflict is recorded. Returns `{ models: ModelEntry[], conflicts: ConflictEntry[] }` where each `ConflictEntry` contains `{ defaultEntry: ModelEntry, localEntry: ModelEntry, reason: 'slug_collision' }`. The frontend displays conflicts to the user so they can resolve them (e.g., rename their local model's slug to make room for the new default)
- `isModelReferenced(modelId: string)` → reads `assignments.json`, returns `{ referenced: boolean, usages: string[] }` where `usages` lists the persona IDs and/or `'default'` that reference this model UUID
- `getResolvedAssignments()` → reads `assignments.json` (UUID values) and `local.json` (registry), builds a UUID-to-slug map, and returns `{ default_model_slug: string | null, persona_models: Record<string, string> }` with slugs as values. Returns `null` for `default_model_slug` when `default_model_uuid` is absent or references an unknown model. Persona entries with unresolvable UUIDs are omitted (graceful degradation). When `assignments.json` does not exist, returns `{ default_model_slug: null, persona_models: {} }`. This is the function used by API consumers; the build system and orchestrator perform equivalent resolution locally by reading both files directly

### 4. Create model registry API handlers

Create `mcp-server/gui/api-models.ts` with handlers following the `api-repos.ts` pattern:

**Model Registry endpoints:**
- `handleGetModels()` → calls `readModels()`, returns the model array. Auto-initializes `local.json` from defaults on first access (handled internally by `readModels()`)
- `handleSaveModels(body)` → accepts the full model array from the frontend. Assigns a new UUIDv4 `id` to any entry where `id` is missing or empty (new models added by the frontend). Delegates to `writeModels()` which handles validation (schema, slug uniqueness, reserved slug enforcement for both new and existing entries) and deletion guards (referenced models cannot be removed — checked by UUID). On success, returns `{ saved: true, models: [...] }`. On failure due to referenced-model deletion, returns 409 Conflict with `{ saved: false, referencedModels: [...] }` listing which models are still in use and which persona assignments reference them, directing the user to the Replace Model feature on the Persona Models tab
- `handleLoadDefaults()` → calls `loadDefaults()`, returns `{ models: [...], conflicts: [...] }`. The frontend displays any conflicts (slug collisions between default entries and existing local entries) so the user can resolve them manually (e.g., rename their local model's slug)

**Model Assignments endpoints:**
- `handleGetAssignments()` → returns current assignments enriched with a `stale: boolean` field. Staleness is determined by comparing `max(mtime(assignments.json) ?? 0, mtime(local.json) ?? 0)` against `mtime(name-mapping.json)` — if either user-modified model file is newer than `name-mapping.json` (or `name-mapping.json` doesn't exist), `stale` is `true`. This catches registry changes (renames, `cc_model` edits) that don't touch `assignments.json` but still make generated persona output stale. `default.json` is excluded from the comparison: its mtime reflects Git checkout time (reset by `git pull`), not user modification time; when the user loads defaults, `local.json` is written and its mtime naturally propagates staleness. When neither `local.json` nor `assignments.json` exists, `stale` is `false` (no user overrides = nothing to rebuild)
- `handleUpdateAssignments(body)` → validates all model UUIDs in `persona_models` and `default_model_uuid` exist in the model registry (via `readModels()`) + validates all persona keys are valid persona `id` values from `name-mapping.json`, writes `assignments.json` (UUID values), returns updated assignments (with `stale: true` since the write just made assignments newer than the last build). Returns 400 if `name-mapping.json` does not exist (persona build must run at least once before assignments can be validated)
- `handleReplaceAssignedModel(body)` → accepts `{ old_model_id: string, new_model_id: string }` (UUIDs), validates both UUIDs exist in the model registry, validates `old_model_id !== new_model_id` (returns 400 "Source and target models must be different" if equal), reads `assignments.json`, replaces all occurrences of `old_model_id` UUID with `new_model_id` UUID (in `default_model_uuid` and all `persona_models` values), writes back, returns updated assignments. Returns 400 if `old_model_id` is not referenced anywhere

**Persona Build endpoint:**
- `handleRebuildPersonas(workspaceRoot)` → spawns `node scripts/build-personas.js` as a child process via `child_process.spawn` with `cwd: workspaceRoot`. Collects stdout and stderr. On exit code 0: returns `{ success: true, output: string }`. On non-zero exit: returns `{ success: false, output: string, exitCode: number }` with HTTP 500. The handler is async — it returns a Promise that resolves when the child process exits. A module-level `buildInProgress` flag prevents concurrent builds: if a build is already running, returns 409 Conflict `{ error: 'A persona build is already in progress' }`. The flag is cleared in a `finally` block to ensure cleanup even on unexpected errors. This follows the existing subprocess pattern from `orchestrator-manager.ts` (which uses `spawn` with `WORKSPACE_ROOT`), but uses a non-detached process since the GUI needs to wait for the result

## Assumptions

- `WORKSPACE_ROOT` in the MCP server reliably points to the monorepo root in all deployment scenarios (local development, global install via shim)
- The persona YAML fields `model` / `model_slug` remain as fallback configuration and are not removed
- The `name-mapping.json` consumer (`mcp-server/src/utils/constants.ts` → `AGENT_NAMES`) currently ignores unknown fields, so adding `model` / `model_slug` / `suite` is backward-compatible
- Model slugs are globally unique identifiers — no namespace collision between models in `local.json`
- All three persona suites (ledger, standalone, ledger-support) have build plugins or config that can be extended with model resolution override logic
- For standalone and ledger-support suites, when neither assignments nor per-persona YAML provides a model, the resolved model defaults to `inherit` (Inherit / Auto), yielding `model: "Inherit / Auto"`, `model_slug: "inherit"`, `cc_model: "inherit"` in `name-mapping.json`
- Standalone and ledger-support personas have `id` fields in their YAML metadata that are unique across all suites; these `id` values come directly from each persona's YAML file and do not follow a single uniform naming convention — for example, the standalone Developer persona uses `developer-standalone` and the Ledger Bootstrapper ledger-support persona uses `standalone-ledger-bootstrapper`
- For standalone and ledger-support personas, the `role` field in `name-mapping.json` is derived by stripping the suite suffix from the persona `name` field (e.g., `"Developer (Standalone)"` → `"Developer"`; `" (Ledger Support)"` suffix is stripped equivalently). Ledger personas use the `role:` YAML field directly, which is validated against the workflow manifest. If no recognizable suite suffix is present, `name` is used as-is

## Constraints

- `personas/model-registry/local.json` and `assignments.json` must never be committed to Git
- `default.json` must be committed and maintained as part of the distribution
- The build system and orchestrator must function correctly when `assignments.json` and `local.json` do not exist (first-time users)
- Model slug format: lowercase alphanumeric with hyphens (`/^[a-z0-9]+(-[a-z0-9]+)*$/`)
- The slug `"inherit"` is reserved for the built-in "Inherit / Auto" model — user-created models must not use this slug (enforced on both create and update)
- GUI must handle the empty-registry edge case: show a message directing users to the Model Registry tab when no models are available for assignment
- GUI must handle the pre-build edge case: show a message when `name-mapping.json` does not exist, directing users to run the persona build first
- Assignment keys in `persona_models` are persona `id` values from `name-mapping.json`, not workflow manifest role IDs — this ensures all three suites are covered; assignment values are model UUIDs, resolved to slugs at consumption time via UUID-to-slug resolution against `local.json`

## Risks & Mitigations
| Risk | Mitigation |
|------|------------|
| **`WORKSPACE_ROOT` incorrect in global install** | The global install shim (`install-mcp-global.js`) already derives the workspace root. Document this assumption in Out of Scope; validate in a follow-up if needed. |
| **Race condition: GUI writes assignments while build reads** | Both use atomic writes; reads use `JSON.parse(readFileSync(...))` which is safe against partial writes since `atomicWriteJson` uses temp-then-rename. |
| **Model slug collision during Load Defaults** | `loadDefaults()` detects slug collisions between default and local entries and returns them as conflicts. The frontend displays conflicts so the user can resolve them manually (e.g., rename the local model's slug). No data is lost or silently overwritten. |
| **Orchestrator reads stale assignments after GUI update** | The orchestrator reads assignments at startup only; a restart picks up changes. This matches the current behavior for YAML changes and is acceptable. |
| **Build system reads assignments before GUI has created the file** | `readAssignments()` gracefully returns a default empty structure when the file doesn't exist. |
| **Rebuild button spawns long-running process** | The build is multi-second (2–5s) but not unbounded. The frontend disables the button and shows a spinner. The backend concurrency guard (`buildInProgress` flag + 409) prevents stacking. The `finally` block ensures the flag is always cleared. |
| **Rebuild during unsaved assignment changes** | The rebuild uses the last-saved `assignments.json` on disk, not the in-memory dirty state. This is correct: the banner explicitly says changes need saving first. The save flow creates/updates `assignments.json` → stale banner appears → user clicks rebuild. |
| **"Inherit" slug assigned as orchestrator default** | If the user sets `inherit` as the default model, the orchestrator would have no concrete slug for any unassigned persona. The orchestrator treats `inherit` as "skip override" and falls back to YAML, which always has a concrete slug. The YAML fallback chain (`per-persona YAML` > `_shared.yaml default_model_slug`) guarantees a concrete slug is always resolved. || **Staleness false positive after build with no model changes** | Staleness compares `max(mtime(assignments.json) ?? 0, mtime(local.json) ?? 0)` against `mtime(name-mapping.json)`. A build that doesn't change models still updates `name-mapping.json`'s mtime, clearing the stale flag. This is the correct behavior — any build refreshes the output. `default.json` is excluded from the comparison to prevent spurious stale flags after `git pull`. |
| **Unsaved changes lost on accidental tab switch** | Tab-switch guard shows a confirmation dialog when dirty state exists. Users must explicitly discard to proceed. |
| **`name-mapping.json` missing on fresh install** | `GET /api/personas` returns `[]` (not an error). Persona Models tab displays a pre-build state message. Assignment validation returns 400 with a clear message. |
| **Expanding name-mapping to all suites breaks existing consumers** | A `.filter(e => e.suite === 'ledger')` guard must be added to the `AGENT_NAMES` construction in `mcp-server/src/utils/constants.ts` before `.map(entry => [entry.role, entry])` — without it, standalone entries whose derived roles collide with ledger `AgentRole` values (e.g., `'Developer'`, `'Planner'`) will silently overwrite ledger entries. The filter is the mitigation; it must be implemented as part of Step 11's `constants.ts` changes. |
| **Default model UUIDs change across versions** | Default entries use deterministic zero-namespace UUIDs, hardcoded in `default.json`. These are stable across installations. `loadDefaults()` matches by `id`, so adding a new default in a future release won't collide with existing entries. |
