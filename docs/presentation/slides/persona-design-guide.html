This is the artifact the previous slides have been implicitly describing. Everything I've said about mission, philosophy, tone and constraints is written down in one place, and that document is what I hand to a model when I want a new persona. Three things about it are worth more than its contents. First, it is domain-neutral on purpose. There is no software vocabulary in it. That is not politeness — it is what makes it portable. Other projects of mine, in completely unrelated domains, fetch this exact file over HTTPS and treat it as read-only. If I let project-specific content creep in, I break all of them. Second, it does not assume you have a build system. Most people writing a persona are pasting text into a web assistant, and the guide says explicitly which metadata is a build input and therefore doesn't apply to them. A hand-maintained persona is a first-class case, not a degraded one. Third, and this is the part that surprised me in practice: versioning the guide changed how maintenance works. Each persona records which guide version it last passed an audit against. So when I add a rule — say, the tone stratification rule in v2.7 — I don't have to remember which personas predate it. The stamps tell me. I generate a status table and audit only the stale ones. And the flip side: some personas genuinely can't follow a rule. Rather than fighting the same audit finding every time, the deviation gets documented with its reason, and audits report it as an accepted exception. That's the difference between a guide that gets followed and one that gets quietly ignored. Every changelog entry in that guide came from something going wrong in a real session. It's not theory — it's a scar record.
