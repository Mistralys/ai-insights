Working With Models

AX — Agent Experience

Developer Experience, but for the agent working in your project.

The agents report their own friction.
Missing tooling, a script that only half exists, documentation that contradicts the code, a handoff that arrived without the data it promised.
It goes into the ledger, not into the void.
Observations accumulate across work packages and land in the synthesis report at the end of the project.
Then you fix the environment.
Add the missing script, correct the stale document, tighten the handoff. The next run is smoother — for the agents and for you.

Friction that slows an agent down is usually slowing your colleagues down too.

AX is a term I've started using deliberately, by analogy with DX. If Developer Experience is about how pleasant a codebase is to work in, Agent Experience is the same question asked about the agent. The mechanism is simple: every persona ends its session by reporting genuine friction it hit — tooling that was missing, a script that didn't do what its documentation claimed, context it needed and couldn't find. Most sessions report nothing, and that's the expected outcome. The value is in the exceptions. Two things make this worth having. First, an agent has no social reason to stay quiet. It won't decide the missing script is too small to mention, and it won't assume it's the only one who couldn't find the document. Second, it hits your project cold, every single time. It has no accumulated workarounds, so it trips over exactly the things a new team member would trip over. The pattern I keep seeing: the friction the agents report is almost never agent-specific. Stale documentation, an undocumented build step, a script that needs three environment variables nobody wrote down — that's the onboarding experience for humans as well. Fixing it for the agent fixes it for everyone.
