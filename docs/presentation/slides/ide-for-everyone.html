Working With Models

An IDE Is Not Only for Developers

A workspace you can browse, read, and talk to — that is useful to anyone who owns a body of knowledge.

A business engineer in our division set up an agent workspace to hold and maintain the institutional knowledge of the division.

› Relevant repositories cloned into the workspace, so the agents can read the real systems.
› Connected to Jira and Confluence through MCP servers.
› Specialised personas for discussing projects and the system landscape.

The result is a place where you can ask about a project and get an answer grounded in the division's own material — and where new colleagues can learn the landscape.

Not a single line of code written. Structure, documents, and personas.

This is the slide for everyone in the room who is not a developer — and it's a real example, not a hypothetical. What an IDE actually gives you is three things: a file tree you can navigate, files you can read, and a chat that can see both. None of that is inherently technical. It happens to be where developers live, so that's where the good tooling landed first. What makes this example work is that the agents can read the actual source material — the repositories are in the workspace, and Jira and Confluence are connected through MCP servers, which I'll come back to in Part 3. The agents aren't recalling things from training data. They're reading the division's own documents. The takeaway for the team leads and section heads: the barrier here is not programming ability. It's being willing to organise your material and describe the specialists you want. If you own a domain, you can build this.
